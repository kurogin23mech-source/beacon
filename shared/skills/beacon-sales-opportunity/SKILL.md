# Beacon Sales Opportunity (商談起票 = 良い商談の作法を構築時に担保する入口)

> 営業 (profession=sales) プロジェクトで、商談を対話で立てる正規の入口。開発側の
> 「マイルストーン起票」に相当する。ms-106 e-3528。
>
> なぜスキルにするか: `beacon opportunity add` の CLI 直叩きは必須項目を素通しで
> きてしまう。良い商談の作法 (= 顧客紐付け・開始フェーズ・想定金額・背景の記述) を
> **起票の瞬間に担保**するために、対話スキルを正規の入口にする。作法は soft
> guidance (対話で促す) で、hard block はしない (master = 人間)。設計方針は SPEC
> `wKIjSzgSgFwcFPubMwIX` (お作法は capability に紐付け、メカニクスは共有プリミティブ)。

## 文章の書き方 (Beacon 全体の哲学)

商談タイトルと背景メモは、後で読む人 (非開発者を含む) が 1 行で状況を掴める自然な
日本語で書く。社内略語を持ち込まない。

## 前提条件チェック

Bash ツールで営業プロジェクトかを確認:

```bash
ROOT=$(beacon-find-root) && \
  test "$(python3 -c "import json;print(json.load(open('$ROOT/.beacon/project.json')).get('profession',''))" 2>/dev/null)" = "sales" \
  && echo "SALES_OK" || echo "NOT_SALES"
```

`NOT_SALES` の場合、「営業プロジェクトでのみ使えます」と伝えて終了する。cloud mode で
`project.json` を直接読めない場合は `beacon account list` が動くかで代替判定してよい。

## Step 1: 顧客(Account)の特定 — まず紐付け先を決める

商談は顧客に紐づく。ユーザーの発話や文脈から対象顧客を決める:

- `acc-XX` が分かればそれを使う。
- 顧客名だけなら `beacon account list --json` で照合して `acc-id` を確定する。
- **まだ顧客が無い**場合は、先に顧客を作る必要がある。`BEACON_SALES_SKILL_CALL=1 beacon account add "<会社名>"`
  を実行する (token は e-3760 の直叩き誘導を自身の正規呼び出しで抑える印)。名刺があれば `/beacon-sales-card` を案内する。

顧客が特定できたら `$ACC` として保持する。顧客紐付けは強く推奨 (紐付けのない商談は
後で顧客資産・パイプラインに乗らない) だが、どうしても不明なら紐付けなしも許容する。

## Step 2: 必須項目を対話で埋める (soft guidance)

以下を対話で埋める。埋まっていない項目は 1 つずつ尋ねる。**強制ではなく推奨**として促す:

1. **タイトル** (必須): この商談を一言で。「(会社名) (案件内容)」の形が読みやすい。
2. **開始フェーズ** (推奨、既定は funnel 入口 = 商談準備): 通常は最初のフェーズから。
   既に提案段階なら `提案準備` 等を指定してよい。フェーズ語彙は
   `beacon phase list` で確認できる。
3. **想定金額** (フェーズ依存):
   - 開始フェーズが `商談準備` なら **任意** (まだ規模が固まっていなくてよい)。
   - 開始フェーズが `提案準備` 以降なら **基本必須** (提案の規模 = 想定金額が定まって
     いるべき。e-3527)。未設定のまま進めると後で警告が出ることを伝える。
4. **提案の3行要約** (推奨、e-3526 の description に「形」を与える / e-3766): 単なる背景
   メモでなく、**「[顧客の課題] を [勝ち筋 = なぜこの顧客が我々から買うのか] に沿って
   [提案] で解決する」の3行要約**にする。可能なら **Account の顧客ドキュメント (dossier)
   から導く**:

   ```bash
   beacon doc show dossier-$ACC   # 顧客の課題 / 勝ち筋 を読む
   ```

   dossier があれば、そこに書かれた顧客の課題と勝ち筋に沿って提案要約を組み立てる
   (顧客理解に基づく提案の芯)。dossier がまだ薄い/無い場合は分かる範囲で書けばよく、
   **無理に埋めさせない**。この3行が、以降どの動線 (提案メール/面談/cockpit) でも
   「顧客理解に沿った提案になっているか」を AI が照合する基準になる。
5. **ボール** (既定 self): 起票直後は通常こちら (self) がボールを持つ。

## Step 3: 起票する

集めた項目で商談を作る。フェーズ活動 (このフェーズの標準ステップ) は `opportunity add`
が自動で seed するので、起票直後から「次にやること」が並ぶ。

```bash
# BEACON_SALES_SKILL_CALL=1 は「これはスキル経由の正規起票」の印 (e-3760)。
# これにより直叩き誘導 nudge を自身の呼び出しでは出さない (作法は既にこのスキルで担保済)。
BEACON_SALES_SKILL_CALL=1 beacon opportunity add "<タイトル>" \
  --account "$ACC" \
  [--phase "<開始フェーズ>"] \
  [--goal <想定金額(円)>] \
  [--description "<背景・経緯>"] \
  [--ball self]
```

- 開始フェーズを省略すると funnel 入口 (商談準備) になる。
- 出力の `opp-XX` を `$OPP` として保持する。seeded 行 (フェーズ活動 N 件) を確認する。

想定金額を後から入れる/直す場合は `beacon opportunity amount $OPP <円>`、背景を後から
足す場合は `beacon opportunity describe $OPP "<text>"`。

## Step 4: 起票確認

`$OPP` の作成内容 (タイトル・顧客・フェーズ・金額・背景・seed された活動) を 1〜2 行で
提示する。「$ACC の商談 $OPP を起票しました。次のステップが N 件並んでいます」。

## Step 5: 次の一手を提案する (target を前進させる)

> Beacon 行動原則: どの操作も最後に「この target を次に前進させる一手」を提示する
> (CORE doc `target-advancement-frame`)。マイルストーン追加後に SPEC 作成を促すのと
> 同じく、商談起票後は次の営業アクションを offer する。

seed されたフェーズ活動の先頭 (通常「初回面談を打診」等) を踏まえ、**次の一手を offer**
する。例:

- 「初回面談の打診メールを今書きますか？」→ 承認されたら `/beacon-sales-email` に橋渡し。
- 「初回面談の日程を調整しますか？」→ `/beacon-sales-schedule` に橋渡し。

**重要 (送信承認)**: 打診メールなど**外向きの送信は自動で行わない**。`/beacon-sales-email`
が下書き→送信アカウント照合→**人間承認**→送信の流れで扱う (誤爆防止の送信承認ゲート)。
このスキルは「起票の勢いで次の一手に橋渡しする」ところまでで、送信はしない。

ユーザーが「今はいい」なら、seed された活動が残るので後から `/beacon-sales-cockpit`
(今日やること) で拾える旨を添えて終了する。

## 制約

- **soft guidance**: 必須項目は対話で促すが hard block しない (master = 人間)。
- **起票は自動、外向き送信は承認付き**: opportunity add / フェーズ活動 seed / 背景記述は
  自動。打診メールなどの外向きは別スキルの送信承認を通す。
- **顧客紐付けを強く推奨**: 紐付けのない商談はパイプライン・顧客資産に乗らない。
- 読み取り (account list / phase list) は安全。書き込みは opportunity add / amount /
  describe のみ。
