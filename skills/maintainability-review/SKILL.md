# Maintainability Review (AI 保守性レビュー) — cold reviewer harness

> このスキルは **計器** である。呼ばれたエージェントは、コードを書いた本人では
> ない「事前文脈ゼロの読み手」として振る舞い、**原典 = コード保守性原則** と
> **変更差分 (または実装)** を突き合わせて、「次の AI が安全に変更できるか」を
> 劣化させる箇所だけを findings として返す。AX レビュー (`ax-review`) と同じ
> review-kernel (原典 + cold judge + 構造化 findings) を、原典を差し替えて再利用
> した **第3 instance** (ms-119、data 駆動 registry で追加)。

## 大前提 (計器の姿勢)

- **測るのは「使う体験 (AX)」ではなく「変える体験 (保守性)」**。同じ「AI 体験」
  でもオペレータが違う (叩く AI vs 直す AI)。interface の使いやすさは AX の領分、
  ここでは **コードの変えやすさ** だけを見る。
- **北極星は「コンテキスト経済」**: 「事前文脈ゼロのエージェントが、変更したい箇所の
  局所だけを読んで、全体を知らずに安全に変えられるか」。全体を頭に載せている author
  には見えない「変えにくさ」を、文脈ゼロの計器が代わりに測る。
- **実装側の自己弁護を採らない**。「この設計はこう意図した」というコミットメッセージや
  コメントの主張は根拠にしない。原典 (保守性原則) と、コードが実際にどう組まれて
  いるかの観測事実だけを突き合わせる。
- **保守性 drift ≠ バグ**。正しく動くが、次の AI が安全に変えにくい構造 (散在・強
  結合・巨大関数・並行コピー・嘘の名前・流儀の不一致・テスト不能) がレビュー対象。
  動作の正しさ (バグ) は別スキルの領分。

> **独立実行の契約 (ms-119 e-3947)**: この計器は、対象を実装した本人のセッションで
> **inline に走らせてはならない** (author は全体を頭に載せているので変えにくさが
> 見えない = 計器が濁る)。必ず `/beacon-review-run maintainability` 経由で、原典
> (保守性原則) + 機械採取した diff だけを渡した **新しいサブエージェント** として
> 走らせる。あなたがこの本文を読んでいるなら独立サブエージェントである前提。実装者
> セッションで読み始めていたら判定を止めて `/beacon-review-run` に投げ直すこと。

## レビュー mode (2 つ、入力で宣言する)

- **diff mode** (完了主張時 / PR レビュー時): 対象は変更差分。問いは「**この変更は
  既存コードの変えやすさを新規に劣化させるか / 既存の保守性欠陥に触れているか**」。
  軽量。現状の主用途。
- **full mode** (コードベース健康監査): 対象は実装スナップショット全体。問いは
  「**実装全体が保守しやすい構造か**」。網羅的だが、結合度など機械採取しにくい性質を
  含むため follow-up (surface 採取器の拡張が要る)。

**入力に mode 宣言が無ければ diff とみなす** (変更レビューが既定用途)。

## 入力

1. **原典**: `skills/maintainability-review/principles.md` (保守性原則、固定)。kernel が
   `beacon review context --type maintainability` で自動添付する (repo-file origin)。
   `--origin-doc` は取らない (原典は capability 同梱で固定、AX と同じ)。
2. **実装 artifact**: diff mode なら変更差分 (`git diff` / PR diff)、full mode なら
   実装 surface。kernel が機械採取する。

### artifact の衛生 (計器を濁さないための線引き)

artifact に載せてよいのは **コードの観測事実** (差分 / 関数の形 / 依存 / 名前 / 実際の
構造)。**実装側の意図説明** は根拠として採らない — それを信じると計器が「author の
説明どおり保守しやすい」と誤診する。原典が求める性質と、コードが実際にどう組まれて
いるかを、それぞれ独立に読む。

## 手順

1. 原典の **7 原則** (局所性 / 単一真実源 / 適切なサイズ / 疎結合 / 名前が予告する /
   一貫性 / 速いフィードバック) を、それぞれ独立したレンズとして diff に当てる。
2. 各レンズで「この変更は次の AI の安全な変更を妨げるか」を、**局所推論の視点**で
   判定する (= 変更対象の局所だけを見て、全体を知らずに安全に変えられるか)。
3. drift (変えにくさの新規持ち込み / 既存欠陥への接触) ごとに finding を 1 件起こす。
4. **機械ガードで既に閉じている性質は二重に挙げない** (原典 §4)。対象リポが
   cli-drift / parity 等のガードで単一真実源・一貫性を構造強制しているなら、それは
   `faithful_observations` に回し、ガードが無い残余だけを finding にする。
5. 保守しやすい良い構造は `faithful_observations` に残す (原典育成に還元)。

## 出力 (JSON)

```json
{
  "mode": "diff | full",
  "target": "PR #479 / ms-119 / ref range",
  "origin_ref": "skills/maintainability-review/principles.md",
  "findings": [
    {
      "principle": "§原則 4 疎結合 (原典のどの原則か)",
      "location": "file:func / 行 (どこの話か)",
      "observed": "コードが実際にどう組まれているか (観測事実)",
      "why_hard_to_change": "次の AI が局所だけ読んで安全に変えられない理由",
      "structural_fix": "変えやすくする構造的な直し方 (助言)",
      "origin": "introduced | touched",
      "severity": "high | medium | low",
      "confidence": "high | medium | low"
    }
  ],
  "faithful_observations": [
    "保守しやすい良い構造、またはガードで既に閉じている性質。無ければ空配列"
  ],
  "skill_gaps": [
    "情報不足 / 指示の曖昧さ / 出力形式の決めにくさを 1 件 = 配列 1 要素で列挙。必須。空なら空配列"
  ]
}
```

### 出力スキーマ規約

- `principle`: 原典の **どの原則** に照らした finding かを必ず示す。
- `observed` / `why_hard_to_change` を **必ず対で書く**。「コードはこう組まれている /
  だから次の AI がこう変えにくい」の対比が drift の証拠。片方だけの断定は禁止。
- `structural_fix`: 「お願い」ではなく **構造の直し方** を書く (関数を切り出す / 単一
  真実源に寄せる / 継ぎ目を作る等)。
- `origin` (初回 dogfood の skill_gap より): この変更が保守性欠陥を **`introduced`
  (新規に持ち込んだ)** のか、既存の負債に **`touched` (触れた・実質拡大した)** のかを
  区別する。diff mode では「巨大な既存 god module に倣って足した」ような finding は
  `touched` であり、author の diff 起因の劣化 (`introduced`) と severity だけでは
  混ざる。この軸があると author に公平で、修正の優先順位も付けやすい (`introduced`
  を優先、`touched` は別途の負債返済 task へ)。
- `severity`: 原典 §4 に従う (high=安全な変更が実質不可能 / medium=妨げるが注意すれば
  可 / low=読みにくいが変更は安全)。
- `confidence` (任意): 確信が持てないが変えにくさの疑いが濃いものは `low` で残す。
- `faithful_observations`: 良い構造 + ガードで閉じている性質。無ければ空配列。
- `skill_gaps` は **必須**。空なら空配列。
- **助言・非 blocking**: findings は「ここが変えにくい、直すか?」の提示まで。verdict を
  確定しない (目的達成レビューと違い、保守性 drift は discoverable な助言)。
- **出力言語**: 呼び出し文脈の言語に合わせる。指定が無ければ呼び出し側に倣う。

## やらないこと

- 正しさ (バグ) のレビューはしない (PR レビューの領分)。動くかは問わない。
- SPEC 忠実度のレビューはしない (思想レビューの領分)。
- interface の使いやすさ (AX) のレビューはしない (`ax-review` の領分、オペレータが違う)。
- 目的達成の verdict は確定しない (人間が持つ)。
- 自動修正はしない (提示まで)。
- 実装の意図説明を読んで「本当は保守しやすい」と補完しない (計器が濁る)。
