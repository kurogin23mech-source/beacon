# Beacon Vision

> ふわっとしたアイデアを対話で精緻化し、構造化ビジョンとして記録する。フォーム入力ではなく対話駆動。

## 前提条件チェック

Bash ツールで以下を実行:
```bash
test -f .beacon/project.json && echo "OK" || echo "NO_BEACON"
```
- `NO_BEACON` の場合、このSkillは何もせず終了する。

## Step 0: 既存ドキュメントの確認

Bash ツールで:
```bash
beacon doc show project-vision 2>/dev/null
```

既に存在する場合、最初に確認する:
```
プロジェクトビジョンドキュメントがあります。

[既存内容のサマリーを2-3文で]

今回は:
  1) 既存を更新する（変えたい部分・追加したい部分を会話で話す）
  2) ゼロから書き直す
  3) 何もしない

どうしますか？
```

ユーザーが「2」または「ゼロから」を選んだ場合、または存在しない場合は Step 1 に進む。

## Step 1: オープニング

**フォーム式の質問は禁止。** 「大目的は？」「ターゲットは？」のような直接質問は **絶対にしない**。

代わりに、こう切り出す:
```
やりたいこと、つくりたいもの、変えたいこと——思いついたまま話してください。「○○みたいなやつ」「△△をなんとかしたい」くらいの粒度で大丈夫です。一緒に少しずつ形にしていきましょう。
```

ユーザーの最初の発言を待つ。

## Step 2: 対話駆動の精緻化

### 6セクション（内部追跡用、ユーザーには見せない）

```
vision_draft = {
  "大目的":         "<unknown | vague: ... | fill: ...>"
  "ターゲット":     "<unknown | vague: ... | fill: ...>"
  "問題":           "<unknown | vague: ... | fill: ...>"
  "成功基準":       "<unknown | vague: ... | fill: ...>"
  "制約":           "<unknown | vague: ... | fill: ...>"
  "やらないこと":    "<unknown | vague: ... | fill: ...>"
}
```

ユーザーの発言ごとに、複数セクションが同時に埋まる可能性がある。それぞれを内部で更新する。

### 対話原則

1. **一度に1問だけ** ユーザーが処理しきれない量を投げない
2. **最も曖昧 or 重要な空白を掘る** unknown ＞ vague の順で優先
3. **ユーザーの言葉を使う** 専門用語・PM用語（KPI、ペルソナ、スコープ等）は使わない。ユーザーが言った単語を会話に取り込む
4. **解決策に飛ばない** 「こういうツールを作るんですね？」のような決め打ちをしない。問題理解に留める
5. **自然な角度から聞く** 「ターゲットは？」と聞くのではなく「これ困ってるの自分だけ？それとも周りも？」のような実感ベース
6. **「わからない」への対応** ユーザーが「わからない」「なんとなく」と答えたら、選択肢を2〜3個提示して反応をもらう（質問の答えやすさを下げる）

### Socratic prompts（参考、必要に応じて使う）

| 掘りたい部分 | 自然な聞き方の例 |
|---|---|
| 大目的（why） | 「なんでこれやりたくなったの？」「これがあったら世界がどう変わる？」 |
| ターゲット | 「これって自分だけが困ってる？周りにもいる？」「思い浮かべてる人いる？」 |
| 問題 | 「具体的にどういうとき詰まる？」「一番イラッとした瞬間は？」 |
| 成功基準 | 「もし完璧に動いたら、どんな流れになってると嬉しい？」「現状の妥協ラインってどこ？」 |
| 制約 | 「お金・時間・技術で縛りある？」「これは絶対無理ってある？」 |
| やらないこと | 「逆にこれだけは絶対やりたくないこと、ある？」「混同しがちだけど切り捨てたい部分は？」 |

### 推測でセクションを埋めるとき

ユーザーの発言から推測可能な部分は、内部状態を「推測:〜」として埋めてOK。ただし **後で確認フェーズで明示する**。

例: ユーザーが「社内プレゼン用に作ってる」と言ったら、ターゲットを「自分（社内プレゼンを作るClaude Code利用者）」と推測。後で「同僚も困ってる？」で広げるかどうか確認。

## Step 3: 終了条件の判定

以下のいずれかを満たしたら Step 4（確認フェーズ）に進む:

- 6セクション中 **4つ以上** が `fill` 状態（推測含む）
- ユーザーが「もうこれくらいで」「だいたいわかったでしょ」と打ち切る発言をした
- 同じ部分を掘ろうとして、ユーザーから新しい情報が出てこない状態が2ターン続いた

## Step 4: 確認フェーズ

これまでの会話を踏まえ、構造化された6セクションを **テキストとして** 提示する:

```
そろそろ整理できそうな感じがしてきたので、いったんまとめてみます。違ったら遠慮なく直してください。

---

**【大目的】**
[1〜2文で。ユーザーの言葉を活かす]

**【ターゲットユーザー】**
[具体的な像を1〜2文。職業・状況・抱えている前提を含める]

**【解決する問題】**
- [箇条書きで具体的な状況]
- ...

**【成功基準（達成したと言える状態）】**
- [箇条書き。可能なら計測可能な形で]
- ...

**【制約・前提】**
- [箇条書き。未確認なら「特に明示なし」と書く]

**【やらないこと】**（推測）
- [箇条書き。推測の場合は明示]
- ...

---

ここまでで「あ、そこ違う」「もっとこうしたい」とかありますか？特に **やらないこと** の部分は推測なので、もし「いやこれも対応したい」「ここは絶対切り捨てたい」あれば教えてください。

問題なければ「OK」と返してもらえれば、ビジョンドキュメントとして記録します。
```

ユーザーから修正があれば、該当部分を更新して再提示。

## Step 5: 書き込み

ユーザーが承認したら Bash ツールで実行:

```bash
beacon doc add "プロジェクトビジョン" --scope core --id project-vision --stdin <<'EOF'
# プロジェクトビジョン

## 大目的

[Step 4 で確定した内容]

## ターゲットユーザー

[Step 4 で確定した内容]

## 解決する問題

[Step 4 で確定した内容]

## 成功基準

[Step 4 で確定した内容]

## 制約・前提

[Step 4 で確定した内容]

## やらないこと

[Step 4 で確定した内容]
EOF
```

**既存ドキュメントを更新する場合** (Step 0 で「更新」を選んだ場合):
```bash
echo "..." | beacon doc update project-vision --stdin
```

## Step 6: 次のステップ案内

書き込み完了後:
```
プロジェクトビジョンを記録しました。

このビジョンを基に、達成までのマイルストーンをフルで描いてみますか？
（実装の道筋を3〜7個のMSに分けて提案します）

「はい」と返してもらえれば、続いて /beacon-roadmap を実行します。
```

ユーザー承認なら `/beacon-roadmap` を起動。

## 制約

- **フォーム入力は絶対にしない**: 「大目的を1文で書いてください」のような直接質問は禁止
- **ユーザーが処理しきれない情報量を投げない**: 一度に1問、長い説明は避ける
- **専門用語を使わない**: ペルソナ・KPI・MVP・PoC等の言葉は出さない（ユーザーが先に使った場合は別）
- **解決策に飛ばない**: 「こういうツール作るんですね？」のような決め付けをせず、問題理解に集中する
- **推測した部分は明示**: AIが補完した部分は「推測」と書き、ユーザーが訂正できる状態にする
