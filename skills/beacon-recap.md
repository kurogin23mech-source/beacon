# Beacon Recap

> 複数プロジェクトを同時に回していても「どこまで進んで、次に何をするはずだったか」を思い出せるようにする動線。横断の一覧 → 各プロジェクトの中身 → 要約までを 1 本で通す。

## このSkillが要る理由

Beacon は「セッションをまたぐと AI は文脈を完全に失う」問題への外部記憶として作られてきた。AI は 1 プロジェクトに専念するので、1 プロジェクト分の深い記録があれば足りる。

**ところが人間は複数プロジェクトを同時に回す。** この立場から必要なのは全情報ではなく **復帰点** —「どこまで進んで、次に何をするはずだったか」だけ。だから「全プロジェクトの状態一覧」をもう 1 枚作るのではなく、**動いたものだけ**を返す。

導出と取得口を足しただけでは誰も呼ばない (このプロジェクトは「配線はあるのに実際には動いていない機能」を 1 マイルストーン分かけて掃討し終えた直後)。このSkillがその最後の 1 本。

## 起動条件

ユーザーが次のように言ったとき:

- 「昨日って何やったっけ」「昨日何してた」「今週何やった」「先週どうだった」
- 「あのプロジェクト直近何やってたっけ」「〇〇プロジェクトどうなってた」
- 「最近動いてるプロジェクトどれ」「どこまで進んでたっけ」
- `/beacon-recap` / `/beacon-recap yesterday` / `/beacon-recap <project> last-week`

**どのプロジェクトのセッションからでも動く。** 横断は所有プロジェクト全体を見るので、cwd を移動したり設定を差し替えたりはしない (CORE doc `ux-principle-no-terminal`)。

## 前提条件チェック

```bash
beacon-find-root >/dev/null && echo "OK" || echo "NO_BEACON"
```

`NO_BEACON` なら何もせず終了する。

## Step 1: 期間を「言われたまま」渡す

**日付を自分で計算してはならない。** ユーザーの言葉をそのまま期間指定に渡す。計算を AI 側でやると、月初・週初・時差の端で静かにずれ、出力からは気づけない。

| ユーザーの言い方 | 渡す値 |
|---|---|
| 昨日 / 昨日って | `yesterday` |
| 今日 / 今日の分 | `today` |
| 今週 | `this-week` |
| 先週 | `last-week` |
| 今月 | `this-month` |
| ここ3日 / 3日分 | `3d` |
| ここ2週間 | `2w` |
| 直近 / 最近 / 指定なし | 省略 (既定 `7d`) |
| 10/14 / 2026-10-14 | `2026-10-14` |
| 10/1〜10/5 | `2026-10-01..2026-10-05` |

受け付けない言い方を渡すと **エラーで止まる** (黙って別の期間に落ちない)。止まったらユーザーに「どの期間ですか」と訊き直す — 勝手に `7d` に読み替えてはならない。

## Step 2: 横断で「動いたプロジェクト」を取る

```bash
beacon recap projects --since <period> --json
```

`--since` を省略すると既定 `7d`。返り JSON:

- `projects[]`: 動いたプロジェクトだけ (`project_id` / `name` / `target_count` / `evidence_count` / `last_evidence_at` / `targets[]`)。**動いていないプロジェクトは入っていない** — これは欠落ではなく設計。
- `project_count`: 動いた数
- `projects_scanned`: 調べた数
- `unavailable[]`: **読めなかった**プロジェクト。「動いていない」ではなく「判定できていない」。1 件でもあれば必ず報告する。
- `unattributed.count` / 各プロジェクトの `unattributed_count`: 出荷の記録のうち対象が特定できていない件数。**これが正で `target_count` が 0 のプロジェクトは「出荷だけで動いた」** ので、一覧から落とさず「本番に出した」と書く。
- `source`: `cloud` (横断) / `local` (このプロジェクト 1 件しか読めていない)

### ここで必ず区別すること

- `project_count == 0` かつ `unavailable == []` → 「この期間に動いたプロジェクトはありません」と言ってよい。
- `unavailable` が空でない → 「動いたのは N 件、ただし M 件は読めていません」と両方言う。**読めなかった分を 0 件側に混ぜない。**
- `source == "local"` → 「このプロジェクト 1 件しか見えていません (横断には cloud mode が必要)」と添える。横断したふりをしない。

## Step 3: 必要なものだけ中身に降りる

ユーザーが特定プロジェクトを名指ししたとき、または Step 2 の結果が 1〜3 件で中身まで見せるのが自然なとき:

```bash
beacon recap targets --project <project_id> --since <period> --json
```

名指しが無い (= 今いるプロジェクトの話) なら `--project` を付けない。

返り JSON の `targets[]` は各要素が `target_id` / `label` / `status` / `evidence_count` / `evidence_by_kind` / `last_evidence_at` / `evidence[]`。`evidence[]` は既定 5 件まで (`--evidence N` で増減、`0` で全件)。`evidence_count` は常に全件数なので、**表示件数を実績として読まない**。

`undated` / `unattributed` / `sources_unavailable` も必ず見る:

- `undated.count > 0` → 「日付が無く期間で判定できなかった記録が N 件あります」と添える。黙って落とすと「無かった」と区別できない。
- `unattributed.count > 0` → **出荷の記録 (push / deploy / release) のうち、どの対象のものか分からないもの**の件数。「プロジェクトは動いているが、対象が特定できていない」と添える。`unattributed.evidence` に中身の行があるので、デプロイした事実は要約に必ず含める (これを落とすと「本番に出した日が何もなかったと返る」= この機能が直した誤答そのものに戻る)。
- `sources_unavailable` が空でない → その種類 (例 `decision`) の動きは件数に入っていない旨を添える。

### 証跡には出荷が含まれる

証跡の種類は対象配下のもの (コミット / PR / 作業項目 / ドキュメント / 判断記録) だけでなく、**プロジェクト直下の出荷の記録** (`push` / `deploy` / `release`) も含む。1 つのデプロイが複数の対象にまたがることがあるので、その場合は各対象に現れる。

**`target_count` が 0 でも「動いていない」とは限らない。** 出荷だけが起きた日は対象ゼロで `moved` が真になる。要約では「対象別に進んだものは無いが、本番に出した」と書く。

## Step 4: 復帰点として要約する

**状態の羅列ではなく、復帰点を書く。** 人間が忘れているのは「どこまで進んで、次に何をするはずだったか」だけ。

プロジェクトごとに:

1. **何が進んだか** を 1〜2 行。証跡の中身 (コミット本文 / タスク名 / 判断記録の内容) を読んで、**ユーザーの言葉で**書く。`evidence_count` の数字だけを並べない (「ms-166 に 18 件」は復帰点にならない)。
2. **次の一手** — その対象が次にどこへ向かうはずだったか。証跡から読めるなら書き、読めないなら「次の一手は不明」と正直に書く。推測を断定しない。

出力形式の目安:

```
2026-10-14 (昨日) — 動いたのは 5 プロジェクト / 12 件中

▸ Beacon — ms-166 を閉じた日
    旗艦 (レビュー採否の構造記録) の穴を 2 本塞いで PR 2 本を取り込み、
    ms-166 を目的達成として閉じた。残余は ms-181 へ。
    次の一手: ms-181 の e-7011 (コミット本文からの判断理由の導出)

▸ profile-extractor — PE プロファイル参照 API
    ms-43 に 10 件 (コミット中心)。社内提供の最小権限設計を進めていた。
    次の一手: 証跡からは読み取れず (中身を見るなら recap targets --project …)

… (以下同様)

⚠ 1 件のプロジェクトは読めませんでした (動いていないのではありません):
    - foo-123: API error 403
※ 日付が無く期間で判定できなかった記録: 6 件
```

### 書き方の原則

Beacon に出す文章は **非開発者を含む読み手** が読めるように書く (CORE doc `entry-writing-principle`)。

- 1 行目は「何が嬉しいか / 何が前に進んだか」をユーザーの言葉で。実装手段を並べない。
- `e-7015` / `ms-184` のような ID の初出には「(何の話か)」を 1 行添える。
- 主語・述語を省略しない (尻切れトンボ禁止)。

## Step 5: target を前進させる一手で終える

Beacon の全Skillの原則どおり、最後に **「この target を次に前進させる一手」** を提示して終える。recap は読み取り専用なので、提示するのは選択肢であって指示ではない:

- 1 プロジェクトに絞って深掘りするか (`beacon recap targets --project <id>`)
- その対象の作業を再開するか (どのプロジェクトの、どの対象か名指しで)
- 止まっているプロジェクトのどれかを畳むか

ユーザーが「これやろう」と選んだら、そのプロジェクトのセッションへ移る話をする (fork / 別セッション)。**recap のセッションで別プロジェクトの実装を始めない** — 1 target = 1 session の原則。

## 制約

- **読み取り専用。** `beacon recap` は両動詞とも read-only。このSkillから `log` / `task` / `milestone` / `summary` 等の書き込みコマンドを実行してはならない。
- **日付を計算しない。** 期間はユーザーの言葉をそのまま `--since` に渡す (Step 1)。
- **読めなかったものを「無かった」にしない。** `unavailable` / `undated` / `unattributed` / `sources_unavailable` は必ず報告する。
- **出荷を落とさない。** デプロイした日に「コミットが N 件」とだけ答えて本番に出したことを書かないのは、この機能が直した誤答そのもの。
- **横断したふりをしない。** `source == "local"` なら 1 件しか見えていないと言う。
- **数字を実績として読まない。** `evidence[]` は既定 5 件までの抜粋、`evidence_count` が全件。進捗率 (`progress`) は AI の自己申告なので、このSkillでは使わない (証跡が真値)。
