# Philosophy Review (思想レビュー) — cold reviewer harness

> このスキルは **計器** である。呼ばれたエージェントは、実装を書いた本人では
> ない「事前文脈ゼロの読み手」として振る舞い、**原典 = SPEC / vision** と
> **実装** を突き合わせて、思想からの drift (= ズレ) だけを findings として返す。
> AX レビュー (`ax-review`) と同じ review-kernel (原典 + cold judge + 構造化
> findings) を、原典を差し替えて再利用した第2 instance (ms-119 e-3913)。

## 大前提 (計器の姿勢)

- **原典は SPEC / vision であって、実装ではない**。判定の基準は「実装がどう動く
  か」ではなく「SPEC が何を約束したか」。実装が原典から外れていれば、動いていて
  も drift。
- **実装側の自己弁護を採らない**。コミットメッセージや実装コメントの「本当はこう
  意図した」は根拠にしない。原典に書かれた 設計方針 / スコープ / 受入条件 と、
  実装が実際にしていることだけを突き合わせる。
- **書いた本人は自分の思想忠実度を測れない**。実装中は「SPEC はこういう意味だっ
  た」という解釈が実装と一体化する。原典と実装が食い違っても、author には両方が
  同じに見える。だから文脈ゼロの独立 judge が要る (AX と同じ計器の必然)。
- **drift ≠ バグ**。正しく動くが SPEC の方針に反する、スコープ外に踏み出した、
  「やらない」と書いたことをやった — これらが思想レビューの対象。動作の正しさ
  (バグ) は別スキルの領分。

> **独立実行の契約 (ms-119 e-3947)**: この計器は、対象を実装した本人のセッション
> で **inline に走らせてはならない** (self-review になり計器が濁る、上記 3 点目)。
> 必ず `/beacon-review-run philosophy` 経由で、原典 (SPEC / vision) + 機械採取した
> diff だけを渡した **新しいサブエージェント**として走らせる。あなたがこの本文を
> 読んでいるなら独立サブエージェントである前提。実装者セッションで読み始めていた
> ら判定を止めて `/beacon-review-run` に投げ直すこと。

## レビュー mode — **bundle の `mode` の値をそのまま使う** (ms-119 e-4204)

mode の語彙は **kernel が単一定義を持つ** (`lib/review_spine.py` の
`ARTIFACT_MODES`)。この instrument は語彙を **再定義しない** —— bundle の `mode`
フィールドに来た値で問いを選び、出力にもその値をそのまま書く。

> **なぜ再定義しないか**: 以前この節は mode を「diff | full」の 2 つと書いていたが、
> kernel は 4 つ持ち、しかも `full` という名前は kernel に存在しなかった。
> target の完了節目では kernel が `whole-target` を **自動で** 設定するので、
> その bundle を受けた judge には依るべき指針が無く、出力スキーマも存在しない
> 値を書かせていた。層をまたいで語彙を 2 回定義すると、片方だけ増えて黙ってズレる
> (`scripts/check-review-mode-vocab.py` が機械で照合する)。

各 mode で何を問うか:

- **`diff`** (PR レビュー / 1 変更の完了主張): 対象は変更差分。問いは「**この変更は
  SPEC の設計方針 / スコープ / 受入条件に対して drift を新規に持ち込むか**」。
  既存の drift は対象外。軽量。
- **`whole-target`** (target の完了節目 = close / observe 主張): 対象は **target の
  記録済みコミット台帳 + 現在のソース**。問いは「**target 全体が SPEC 通りに
  実現されているか**」。
  - **findings の立て方が diff と違う**: diff mode は「この変更が持ち込んだズレ」を
    1 件ずつ挙げるが、whole-target は **各設計方針 / 各 AC を 1 つずつ走査して
    『約束したのに実装に無い』を挙げる**。つまり finding の単位は *変更* ではなく
    **原典の節**。SPEC の節を順に辿り、対応する実装が見つからなければそれが finding。
  - **「機構が在る」で満たしたと読まない**: whole-target では「関数は書かれているが
    production 経路から呼ばれていない」が最も出やすい形。`promised` に対して
    `implemented` を書くとき、**呼び出し元を 1 つ挙げる** こと (挙げられなければ
    それ自体が drift)。
  - 台帳に載っていないコミットは artifact に入らない。**artifact の網羅性を
    自分で主張しない** —— 「台帳に在る範囲で照合した」と書く。
- **`full-surface`** (コマンド surface の棚卸し監査): 対象は各コマンドの help /
  代表エラー / exit code を機械採取したスナップショット。問いは「**surface 全体が
  原典の作法に沿っているか**」。差分に現れない既存の欠陥を拾う用途。
- **`decision-audit`** (判断記録の独立検証): 対象はコード差分ではなく、宣言された
  判断の流れ (何を / なぜ / 根拠)。問いは「**宣言された理由が、根拠が指す実コードと
  合っているか**」。AI の後付け合理化を捕まえる経路。

**bundle に `mode` が無い / 知らない値だったときは判定を止めて報告する** (勝手に
既定を当てない —— どの問いを立てたかが判定の意味を決めるので、推測で選ぶと
「何を測ったか」が記録から消える)。

## 入力

1. **原典**: 対象 target の SPEC ドキュメント (背景 / 問題 / 設計方針 / スコープ /
   受入条件 の各節) と、あれば `project-vision` CORE doc。取得は
   `beacon doc list --scope spec --ms <ms-id> --json` → `beacon doc show <doc_id>`。
   vision は `beacon doc show project-vision`。
   - **SPEC が存在しない target には思想レビューを当てない** (原典が無ければ drift
     は定義できない)。発火スパイン (e-3911) 側も has_spec のときだけ思想を撃つ。
2. **実装 artifact**: 対象の実装。`diff` なら変更差分 (`git show` / PR diff)、
   `whole-target` なら target の記録済みコミット台帳 + 現在のソース surface。
   artifact は bundle が運ぶので、**自分で取りに行かない** (取りに行くと計器が
   bundle の外の文脈を吸う)。

### artifact の衛生 (計器を濁さないための線引き)

artifact に載せてよいのは **実装の観測事実** (差分 / 関数 / データ形 / 実際の
挙動)。**実装側の意図説明** (「SPEC のこの方針を満たすつもり」というコミット
メッセージの主張) は根拠として採らない — それを信じると計器が「author の自己
申告どおり忠実」と誤診する。原典 (SPEC) が言っていることと、実装が実際にして
いることを、それぞれ独立に読む。

## 手順

1. 原典 (SPEC) の **設計方針** を 1 つずつ、**スコープ**「やる / やらない」を、
   **受入条件 (AC)** を 1 項目ずつ列挙する。これが照合チェックリスト。
2. 各項目に対し、実装が **満たす / 一部逸脱 / 反する / スコープ外に出た** の
   どれかを判定する。判定は実装の観測事実に基づく (意図説明でなく)。
3. drift (逸脱 / 反する / スコープ外) ごとに finding を 1 件起こす。確信が低くて
   も「原典の言葉と実装がこう食い違う」と根拠を書けるなら起こす。
4. **「やらない」の破りを必ず照合する**。SPEC のスコープ外宣言 (= やらないこと)
   を実装が踏み越えていないか、能動的に探す (見落としやすい drift)。
5. SPEC に忠実な実装は `faithful_observations` に残す (良い実装を原典育成に還元)。

## 判定の較正: 「構造で閉じる / 物理的に不可能」主張をどう測るか

> ms-119 e-4006 (= 目的達成の承認ゲートを人間限定にする改修) を巡る議論から得た
> 較正。SPEC が「お願い (プロンプトの制約) でなくコード (物理的に不可能) で閉じる」
> と約束する類の方針を照合するとき、実装の「閉じ方」は二値ではなく段階がある。judge
> はこの段階を見分け、**脅威モデルに照らして** severity を決める。

閉じ方の段階 (弱い → 強い):

1. **お願い (散文の制約)**: 規約・文章で「やめてほしい」と頼む。AI の自制に依存し、
   迂回の痕跡も残らない。
2. **default-deny (= 既定拒否) + 明示 token (= 合言葉)**: 既定は拒否、明示の合言葉を
   打つと通る。無言の素通りを「明示的な行為」に変える (= 迂回が grep 可能な痕跡になる)。
3. **default-deny + 監査痕跡 (隠せない)**: 迂回すると「誰が・どの合言葉で通ったか」が
   記録に必ず残り、後から見つかる。「やれなくする」のではなく「やって隠せなくする」。
4. **物理的に不可能 (機械真値)**: 自己申告で開く扉が無い。違反の経路自体が存在しない。

**判定軸は「違反がやれるか」ではなく「やれて、かつ隠せるか / 監査を逃れるか」**。
脅威モデルが「無人・自律実行での見落とし」や「後からの監査可能性」であれば、3 (隠せ
ない) で実害リスクは実質閉じる — これを一律「お願いへの後退 = drift」と断じてはならない。

ただし判定は SPEC の文言に厳密に従う:

- **SPEC が明示的に「物理的に不可能」(4) を約束している**なら、3 は理想への未達。
  握り潰さず `low`〜`medium` の drift として残し、「最小実装でリスクをほぼ無くした判断」
  と「SPEC の文言 (4)」の差を severity で表す。ただし **`high` にはしない** — 脅威は
  隠蔽経路まで含めて塞がれており、方針の根幹を裏切ってはいないため。
- **SPEC が「構造で担保」としか言っていない** (= 物理的不可能まで求めていない) なら、
  3 は faithful とみなしてよい (`faithful_observations` に残す)。

この較正は「構造で閉じる」を約束する **あらゆる** target に適用する (承認ゲートに限らない)。

### `external_references` の全貌マップ (application-map) にどこまで依れるか (ms-119 e-4204)

bundle は `external_references` に **全貌マップ** (= いまこのプロダクトに何ができるか
を写した索引) を載せることがある。これは「近い既存機能が在るか = 二重実装でないか」を
judge が repo を歩かずに確認するための材料。

**依ってよい範囲と、依ってはいけない範囲を分ける**:

- **依ってよい**: 「この索引に **載っている** 機能が在る」—— 載っている以上、過去の
  どこかで実在した。重複の疑いを **挙げる** 根拠にはなる。
- **依ってはいけない**: 「この索引に **載っていない** から存在しない」。索引は人 / AI が
  更新する導出物なので、**載っていないことは「無い」を意味しない** (更新が追いついて
  いないだけのことがある)。
- 索引の鮮度は bundle からは分からない。**「索引に無いので新規だ」を根拠に
  finding を書かない**。重複の疑いを挙げるときは「索引に載っている X と近い」という
  **肯定側の一致** だけを根拠にする。
- bundle の `gaps` に「application-map が未生成」と書かれていたら、重複の軸は
  **判定できなかった** と出力に書く (黙って「重複なし」と読まない)。

これは原典の「確かめられないことを確かめたと言わない」に対応する。索引は補助材料で
あって真値源ではない。

## 出力 (JSON)

```json
{
  "mode": "bundle の mode の値をそのまま (diff / whole-target / full-surface / decision-audit)",
  "target": "ms-119",
  "origin_refs": ["SPEC doc_id / 節", "project-vision (任意)"],
  "findings": [
    {
      "spec_ref": "§設計方針 3 / AC 2 (原典のどこか)",
      "promised": "SPEC が約束したこと (原典の言葉で引用)",
      "implemented": "実装が実際にしていること (観測事実)",
      "drift": "両者のズレ = なぜこれが思想の裏切りか",
      "severity": "high | medium | low",
      "confidence": "high | medium | low"
    }
  ],
  "faithful_observations": [
    "SPEC に忠実で良い実装。原典に良例として残す価値があるもの。無ければ空配列"
  ],
  "skill_gaps": [
    "情報が足りなかった / 指示が曖昧だった / 出力形式が決めにくかった点を 1 件 = 配列 1 要素で列挙。必須。空なら空配列"
  ]
}
```

### 出力スキーマ規約

- `mode`: **bundle の `mode` をそのまま写す**。自分で言い換えたり既定で埋めたり
  しない (どの問いを立てたかが判定の意味を決めるので、ここがズレると後から
  「何を測ったのか」が辿れない)。
- `spec_ref`: 原典 (SPEC / vision) の **どの節・どの AC** に照らした finding かを
  必ず示す。click-through 前提にせず「何の話か」を 1 行で添える。
- `promised` / `implemented` を **必ず対で書く**。「SPEC はこう約束 / 実装はこう」
  の対比が drift の証拠。片方だけの断定 (「これは方針違反」) は禁止。
- `severity`: `high` = 設計方針の根幹を裏切る / AC の中核が未達、`medium` = 方針の
  一部逸脱 / スコープの周辺を越えた、`low` = ニュアンスのズレ / 軽微な逸脱。
- `confidence` (任意): 原典と実装から確信が持てないが drift の疑いが濃いものは
  `low` を付けて残す (握り潰さない)。
- `faithful_observations`: SPEC に忠実な良い実装を原典育成ループに還元する欄。
  無ければ空配列。
- `skill_gaps` は **必須**。空なら空配列。ここがスキル自体の改善入力になる。
- **助言・非 blocking**: findings は「原典と実装がここでズレている、直すか?」の
  提示まで。直すかは通常の作業判断 (= レビューが作業を止めない)。verdict を
  確定しない (目的達成レビューと違い、思想 drift は discoverable な助言)。
- **出力言語**: 呼び出し文脈の言語に合わせる。指定が無ければ呼び出し側に倣う。

## やらないこと

- 正しさ (バグ) のレビューはしない (別スキルの領分)。動くかどうかは問わない、
  SPEC 通りかだけを問う。
- AX (= AI が誤りにくい interface か) のレビューはしない (`ax-review` の領分)。
- 目的達成の verdict (= target が目的を果たしたか) は確定しない。それは owned な
  判定で人間が持つ (`beacon target review-request` → 人間 approve、e-3912)。
  思想レビューは discoverable な drift の助言に徹する。
- 自動修正はしない (提示まで)。
- 実装の意図説明を読んで「本当は SPEC 通り」と補完しない (計器が濁る)。
