# Philosophy Review (思想レビュー) — cold reviewer harness

> このスキルは **計器** である。呼ばれたエージェントは、実装を書いた本人では
> ない「事前文脈ゼロの読み手」として振る舞い、**原典 = SPEC / vision** と
> **実装** を突き合わせて、思想からの drift (= ズレ) だけを findings として返す。
> AX レビュー (`ax-review`) と同じ review-kernel (原典 + cold judge + 構造化
> findings) を、原典を差し替えて再利用した第2 instance (ms-119 e-3913)。

## 大前提 (計器の姿勢)

- **原典は SPEC / vision であって、実装ではない**。判定の基準は「実装がどう動く
  か」ではなく「SPEC が何を約束したか」。実装が原典から外れていれば、動いていて
  も drift。
- **実装側の自己弁護を採らない**。コミットメッセージや実装コメントの「本当はこう
  意図した」は根拠にしない。原典に書かれた 設計方針 / スコープ / 受入条件 と、
  実装が実際にしていることだけを突き合わせる。
- **書いた本人は自分の思想忠実度を測れない**。実装中は「SPEC はこういう意味だっ
  た」という解釈が実装と一体化する。原典と実装が食い違っても、author には両方が
  同じに見える。だから文脈ゼロの独立 judge が要る (AX と同じ計器の必然)。
- **drift ≠ バグ**。正しく動くが SPEC の方針に反する、スコープ外に踏み出した、
  「やらない」と書いたことをやった — これらが思想レビューの対象。動作の正しさ
  (バグ) は別スキルの領分。

## レビュー mode (2 つ、入力で宣言する)

- **diff mode** (完了主張時 / PR レビュー時): 対象は変更差分。問いは「**この変更
  は SPEC の設計方針 / スコープ / 受入条件に対して drift を新規に持ち込むか**」。
  既存の drift は対象外。軽量。
- **full mode** (target 完了時の総点検 / 監査): 対象は target 実装のスナップ
  ショット全体。問いは「**実装全体が SPEC 通りに実現されているか**」。網羅的に、
  各設計方針 / 各 AC を 1 つずつ照合する。

**入力に mode 宣言が無ければ full とみなす** (完了主張の総点検が既定用途)。

## 入力

1. **原典**: 対象 target の SPEC ドキュメント (背景 / 問題 / 設計方針 / スコープ /
   受入条件 の各節) と、あれば `project-vision` CORE doc。取得は
   `beacon doc list --scope spec --ms <ms-id> --json` → `beacon doc show <doc_id>`。
   vision は `beacon doc show project-vision`。
   - **SPEC が存在しない target には思想レビューを当てない** (原典が無ければ drift
     は定義できない)。発火スパイン (e-3911) 側も has_spec のときだけ思想を撃つ。
2. **実装 artifact**: 対象の実装。diff mode なら変更差分 (`git show` / PR diff)、
   full mode なら関連コミット群 + 現在のソース surface。

### artifact の衛生 (計器を濁さないための線引き)

artifact に載せてよいのは **実装の観測事実** (差分 / 関数 / データ形 / 実際の
挙動)。**実装側の意図説明** (「SPEC のこの方針を満たすつもり」というコミット
メッセージの主張) は根拠として採らない — それを信じると計器が「author の自己
申告どおり忠実」と誤診する。原典 (SPEC) が言っていることと、実装が実際にして
いることを、それぞれ独立に読む。

## 手順

1. 原典 (SPEC) の **設計方針** を 1 つずつ、**スコープ**「やる / やらない」を、
   **受入条件 (AC)** を 1 項目ずつ列挙する。これが照合チェックリスト。
2. 各項目に対し、実装が **満たす / 一部逸脱 / 反する / スコープ外に出た** の
   どれかを判定する。判定は実装の観測事実に基づく (意図説明でなく)。
3. drift (逸脱 / 反する / スコープ外) ごとに finding を 1 件起こす。確信が低くて
   も「原典の言葉と実装がこう食い違う」と根拠を書けるなら起こす。
4. **「やらない」の破りを必ず照合する**。SPEC のスコープ外宣言 (= やらないこと)
   を実装が踏み越えていないか、能動的に探す (見落としやすい drift)。
5. SPEC に忠実な実装は `faithful_observations` に残す (良い実装を原典育成に還元)。

## 出力 (JSON)

```json
{
  "mode": "diff | full",
  "target": "ms-119",
  "origin_refs": ["SPEC doc_id / 節", "project-vision (任意)"],
  "findings": [
    {
      "spec_ref": "§設計方針 3 / AC 2 (原典のどこか)",
      "promised": "SPEC が約束したこと (原典の言葉で引用)",
      "implemented": "実装が実際にしていること (観測事実)",
      "drift": "両者のズレ = なぜこれが思想の裏切りか",
      "severity": "high | medium | low",
      "confidence": "high | medium | low"
    }
  ],
  "faithful_observations": [
    "SPEC に忠実で良い実装。原典に良例として残す価値があるもの。無ければ空配列"
  ],
  "skill_gaps": [
    "情報が足りなかった / 指示が曖昧だった / 出力形式が決めにくかった点を 1 件 = 配列 1 要素で列挙。必須。空なら空配列"
  ]
}
```

### 出力スキーマ規約

- `mode`: この実行が diff / full のどちらだったかを明示する。
- `spec_ref`: 原典 (SPEC / vision) の **どの節・どの AC** に照らした finding かを
  必ず示す。click-through 前提にせず「何の話か」を 1 行で添える。
- `promised` / `implemented` を **必ず対で書く**。「SPEC はこう約束 / 実装はこう」
  の対比が drift の証拠。片方だけの断定 (「これは方針違反」) は禁止。
- `severity`: `high` = 設計方針の根幹を裏切る / AC の中核が未達、`medium` = 方針の
  一部逸脱 / スコープの周辺を越えた、`low` = ニュアンスのズレ / 軽微な逸脱。
- `confidence` (任意): 原典と実装から確信が持てないが drift の疑いが濃いものは
  `low` を付けて残す (握り潰さない)。
- `faithful_observations`: SPEC に忠実な良い実装を原典育成ループに還元する欄。
  無ければ空配列。
- `skill_gaps` は **必須**。空なら空配列。ここがスキル自体の改善入力になる。
- **助言・非 blocking**: findings は「原典と実装がここでズレている、直すか?」の
  提示まで。直すかは通常の作業判断 (= レビューが作業を止めない)。verdict を
  確定しない (目的達成レビューと違い、思想 drift は discoverable な助言)。
- **出力言語**: 呼び出し文脈の言語に合わせる。指定が無ければ呼び出し側に倣う。

## やらないこと

- 正しさ (バグ) のレビューはしない (別スキルの領分)。動くかどうかは問わない、
  SPEC 通りかだけを問う。
- AX (= AI が誤りにくい interface か) のレビューはしない (`ax-review` の領分)。
- 目的達成の verdict (= target が目的を果たしたか) は確定しない。それは owned な
  判定で人間が持つ (`beacon target review-request` → 人間 approve、e-3912)。
  思想レビューは discoverable な drift の助言に徹する。
- 自動修正はしない (提示まで)。
- 実装の意図説明を読んで「本当は SPEC 通り」と補完しない (計器が濁る)。
