# AX (AI Experience) レビュー原則 — 原典

> AX レビュー Capability が diff を照合する基準文書 (= 原典)。この doc は
> **Beacon の設計原則ではなく**、AX レビュー Capability に随伴して対象リポを
> 選ばず旅する (= dev インスタンスの Layer 3 Capability の一部)。レビュアー
> (= 計器) が「何を欠陥とみなすか」はすべてここで決まる。

---

## 1. AX とは何か

**AX (= AI Experience)**: AI エージェントが、あるツール (CLI・フィールド・
フラグ・エラー文言・戻り値・スキーマ) を **どれだけ迷わず・誤らず・少ない
やり直しで使えるか**。

DX (= 開発者体験) / UX (= 利用者体験) と同じ抽象度の、独立した品質カテゴリ。
一次オペレータ (= そのツールを主に操作する主体) が AI であるツールには、
人間向けの UX とは別に AX が存在する。

### なぜ独立カテゴリとして立てるのか

UX の一分派として扱うと軽視される。「AX」と名付けることで、これは独立した
評価軸だと構造的に主張でき、原則・レビュー・findings (= 発見事項) が一貫した
枠を持てる。**カテゴリを正しく切ることが設計の半分**。

### AX の操作的定義 (= レビューの基準になる 1 行)

> **事前文脈ゼロのエージェントが、名前とスキーマとエラー文言だけを頼りに、
> どれだけ正しく使えるか。**

「事前文脈ゼロ」がAXの本質。ドキュメントを熟読すれば使えるのは当たり前で、
AX が問うのは「読まなくても・初見でも踏み外さないか」。

---

## 2. 計器の必然 — なぜ書いた本人は AX を測れないか

上の定義を認めると、次が **演繹的に** 導かれる:

- 実装中、書いた本人 (= author) は文脈が最大化する。命名の不一致や隠れた
  副作用に「慣れて」しまい、friction (= つまずき) が見えなくなる。
- つまり author は定義上 AX の値を測れない。慣れが friction を消すため。

したがって **独立した文脈ゼロのエージェントは、客観性のためではなく、
AX の唯一妥当な「計器」**。これはレビュー体制の好みではなく、AX の定義からの
必然。

**レビューの作法もここから決まる**: 計器 (= レビュアー) は author の説明を
読まずに、名前・スキーマ・エラー文言・戻り値だけで判断する。説明を読んだ
瞬間、それは文脈ゼロでなくなり計器として無効になる。

## 3. AX の失敗モード (原則セット)

各原則は「守るべき性質 / 破れの兆候 (= 検出パターン) / なぜ AI に効くか (Why) /
実例」で書く。レビュアーはこの各原則を **独立したレンズ** として diff に当てる。

### 原則 1. 命名の一貫性 (コマンド間・フィールド間)

- **性質**: 同じ概念は、コマンド・フラグ・フィールドを跨いで同じ名前を持つ。
  逆に、違う概念は違う名前を持つ。
- **破れの兆候**: 同概念で別名 / 別概念で同名 / 略記と正式名の混在 /
  同義フラグがコマンドごとに割れる。
- **Why (AI に効く理由)**: AI は命名から意味を類推し、1 度覚えたパターンを
  他コマンドへ転移する。命名不一致はその転移を毒し、静かな誤用を生む。
- **実例**: `beacon doc` / `task` / `log` はマイルストーン指定が `-m`、
  `beacon milestone` は `--ms`。しかも無効な `-m` は黙って無視される
  (→ 原則 2 と複合)。この失敗は L2 記憶層 (= AI の失敗を capability ごとに
  蓄積する記憶) に既に何度も記録されている。

### 原則 2. silent no-op の禁止 (無効入力を黙って捨てない)

- **性質**: 受け付けられない入力は、黙って捨てず、明示的に拒否 or 警告する。
- **破れの兆候**: 無効フラグが無視されて成功扱い / 想定外の引数が握り潰される /
  型不一致が暗黙にキャストされて別物になる。
- **Why**: AI は「エラーが出ない = 成功」と解釈する。silent no-op は誤った
  成功確信を生み、間違いに気づく唯一の機会 (= 失敗の可視化) を奪う。
  **気づけない誤りは、気づける誤りより桁違いに高コスト**。
- **実例**: 複数アクティブ MS の状態で `beacon doc -m <id>` の `-m` が黙って
  無視される。「指定したのに効いていない」を成功として通過してしまう。

### 原則 3. エラーは回復経路を示す (recoverable errors)

- **性質**: 失敗メッセージは「何が悪いか」だけでなく「次にどうすればいいか」
  を含む。
- **破れの兆候**: `invalid argument` だけで Usage を出さない / 修正候補や
  正しい形を示さない / どのフィールドが原因か特定できない。
- **Why**: AI は次のアクションをエラー文言から決める。回復経路が無いと当て
  推量のリトライになり、別の事故 (= 破壊的操作・無限リトライ・コスト) を招く。
- **良い実例**: `beacon task update` は引数不足時に完全な Usage を返す。
  `beacon milestone observe` は「Pass --reason ...」と次の一手を明示する。
  → これらは AX 良好例として原典に残す (悪い例だけでなく良い例も基準になる)。

### 原則 4. フィールドは自己記述的 (self-describing schema)

- **性質**: フィールド / フラグ名は、ソースを読まずとも名前だけで意味と型と
  単位が立つ。
- **破れの兆候**: 曖昧な略語 / 単位のない数値 (`timeout` が秒かミリ秒か不明) /
  bool か enum か名前から分からない / 意味が文脈依存で変わる。
- **Why**: AI はスキーマを一次情報として使う。名前が意味を担わないと、
  ソース読解が毎回必須になり、読まなかったときに誤用する。

### 原則 5. 最小驚き (least surprise)

- **性質**: コマンドは名前が示唆する通りに振る舞う。副作用は予測可能。
- **破れの兆候**: 名前と挙動の乖離 / 隠れた副作用 (例: `status` 系が書き込む /
  read が cursor を進める) / 順序依存の暗黙前提 / モードで意味が反転する。
- **Why**: AI は名前から挙動モデルを組み立て、以後の予測に使う。驚きは
  そのモデルを壊し、当該コマンドだけでなく **周辺の予測すべてを不確実化** する。

### 原則 6 (メタ). 破れは構造で塞ぐ、プロンプトで塞がない

- **性質**: findings が提案する修正は「注意して使え」ではなく「物理的に
  誤りようがない」形にする。
- **Why**: プロンプト (= お願い) の制約は AI が踏み外せる。コード / スキーマ /
  命名の制約は踏み外せない。AX 欠陥は「気をつける」で消えない。命名を揃える・
  無効入力を拒否する・エラーに回復経路を埋める、という構造修正で閉じる。
- この原則は、局所パッチを繰り返さず「入力→変換→出力の全経路を書き出し、
  誰が値を変えられるかを列挙し、構造で防ぐ」というデバッグ思想と地続き。

## 4. severity の付け方 (findings の重み)

| severity | 基準 | 例 |
|---|---|---|
| **high** | 気づけない誤り (silent corruption / silent no-op)、破壊的副作用 | 無効フラグの無視、隠れた書き込み |
| **misleading** | エラーは出る (= silent ではない) が、真因と無関係な文言で誤診を誘発し、誤った回復ループに入らせる | `Milestone not found` (真因は `--reason` の positional 誤流入) / `Entry not found: --help` (真因はヘルプ経路の破れ) |
| **medium** | 気づけるが高頻度で踏む誤り、命名不一致 | `-m` / `--ms` の割れ |
| **low** | 使い勝手を損なうが誤りには直結しない | 冗長な必須フラグ |

原則として **「気づけるか」を第一の severity 軸** に置く。AI にとって最悪なのは
失敗そのものではなく、失敗が可視化されないこと。**misleading は silent と
medium の間**: 失敗は見えるが、エラー文言が真因から AI を遠ざけるため、
「見えているのに直せない」という silent に次ぐ高コストを生む。

---

## 5. finding の形 (レビュー出力の単位)

各 finding は以下を持つ (出力形式は capability 本体が決めるが、意味の骨格は
ここで固定する):

- **原則**: 破った原則番号 (1〜6)
- **surface**: 該当するコマンド / フラグ / フィールド / エラー文言
- **破れの具体**: 何がどう原則を破っているか (diff の該当箇所)
- **なぜ AI が誤るか**: この破れが文脈ゼロのエージェントをどう誤らせるか
- **構造的修正案**: 原則 6 に従い、踏み外しようがなくする修正
- **severity**: high / misleading / medium / low (§4)

---

## 6. レビューの作法 (計器の使い方)

- **対象は diff**。問い: *この変更は上記 6 原則のどれかを新規に破る / 悪化
  させるか*。全 surface の総ざらい (= full-surface audit) は別モードで、PR
  ごとの軽量レビューとは分ける。
- **レビュアーは文脈ゼロの独立エージェント** (= cold subagent)。author の
  意図説明を読まず、名前・スキーマ・エラー・戻り値だけで判断する (§2)。
- **多視点は failure-mode-diverse に**。各原則を別レンズとして独立に当てる。
  同じ観点を N 体に増やす (= redundant) のではなく、命名・no-op・エラー・
  自己記述・驚き を別々のレンズが見る。人間の多数決ではなく、失敗モードの
  網羅が目的。
- **証拠の prior (= 事前情報、optional)**: L2 記憶層に failure / surprise が
  蓄積している capability への変更は、既に転んだ実績があるとみなして厳しく
  採点する。ただし L2 が無い環境でも原則だけでレビューは成立する (= L2 は
  必須依存ではなく増強)。

## 7. この doc 自体の性格 (置き場所の判断軌跡)

- **Beacon CORE ではない**。CORE は Beacon 自身の設計原則。これは Beacon を
  (そして他の何でも) 作るときに使うメタツールの原典。
- dev インスタンス (= 開発職種パッケージ) が持つ横断 Capability (Layer 3、
  いずれ TrailNode で配布しうる領域) に随伴する。だから対象リポを選ばず、
  Beacon の DB (= beacon doc) ではなく **capability と一緒に旅する markdown
  ファイル** として置く。
- ここに書く原則は普遍的 (どの CLI / API にも当たる)。Beacon 固有なのは §6 の
  L2 prior だけで、それも optional。

## 8. 良い AX の例 (full-surface レビューで surface から回収)

原則 3 の「良い実例も基準になる」に従い、計器が拾った良い surface を残す。
新しい surface を設計するときの手本 (= positive_observations の還元先):

- **context-free な安全弁**: `whoami` のような引数ゼロ・読み取り専用・自己記述的な
  identity/role 確認。破壊操作の前に文脈ゼロで叩ける。
- **enum を Usage 行にインライン列挙**: `--status ok|warning|error` /
  `--ball self|counterpart` / `--direction inbound|outbound`。閉じた値域が
  silent 誤分類を防ぐ。
- **ビジネスルールを必須フラグで構造化**: `operation approve --spec <doc-id>`
  (承認は必ず SPEC に紐づく、をプロンプトでなく必須フラグで強制)。
- **状態遷移ガードを Usage に開示**: `operation activate (todo/in_progress -> open)`
  — 状態機械が surface だけから読める。
- **日付書式を placeholder で固定**: `<YYYY-MM-DD>` は書式推測を構造的に消す。
  他の裸の `<date>` / `<datetime>` はこれに倣うべき手本。
- **必須は角括弧なしで明示**: `member remove --reason` のように必須フラグを
  非 optional 表記にすると、実行時エラーなしで必須が伝わる。
- **副作用を名前 / help で開示**: `pr sync --dry-run` / `member join` の
  "bind this cwd"。

- 対の関係: 「AI を安全な経路に強制する」側の仕組み (Skill bypass を構造で
  防ぐ) と、本原典の「経路そのものを踏み外しようがなくする」側は、強制と設計の
  両輪。重複ではなく補完。
- 入力の増強元 (optional): L2 記憶層 (AI の失敗テレメトリ) / アプリケーション
