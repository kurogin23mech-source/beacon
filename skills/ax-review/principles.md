# AX (AI Experience) レビュー原則 — 原典

> AX レビュー Capability が diff を照合する基準文書 (= 原典)。この doc は
> **Beacon の設計原則ではなく**、AX レビュー Capability に随伴して対象リポを
> 選ばず旅する (= dev インスタンスの Layer 3 Capability の一部)。レビュアー
> (= 計器) が「何を欠陥とみなすか」はすべてここで決まる。

---

## 1. AX とは何か

**AX (= AI Experience)**: AI エージェントが、あるツール (CLI・フィールド・
フラグ・エラー文言・戻り値・スキーマ) を **どれだけ迷わず・誤らず・少ない
やり直しで使えるか**。

DX (= 開発者体験) / UX (= 利用者体験) と同じ抽象度の、独立した品質カテゴリ。
一次オペレータ (= そのツールを主に操作する主体) が AI であるツールには、
人間向けの UX とは別に AX が存在する。

### なぜ独立カテゴリとして立てるのか

UX の一分派として扱うと軽視される。「AX」と名付けることで、これは独立した
評価軸だと構造的に主張でき、原則・レビュー・findings (= 発見事項) が一貫した
枠を持てる。**カテゴリを正しく切ることが設計の半分**。

### AX の操作的定義 (= レビューの基準になる 1 行)

> **事前文脈ゼロのエージェントが、名前とスキーマとエラー文言だけを頼りに、
> どれだけ正しく使えるか。**

「事前文脈ゼロ」が AX の本質。ドキュメントを熟読すれば使えるのは当たり前で、
AX が問うのは「読まなくても・初見でも踏み外さないか」。

### 作る側の目的 — AI が表現したいことを、表現できる環境にする

AI 向けの作業環境 (= ハーネス) を作るとき、目的を一行で言うとこれになる。
**AI がやりたいことを 1 つの操作で言えるようにすること。** 道具を増やすことでも、
禁止事項を増やすことでもない。

なぜこれが目的かは、人間と AI の振る舞いの差から出る。人間は手が足りないとき
**「この操作が無い」と言える**。AI は言わずに、持っている操作を組み合わせて
**黙って工夫する**。その工夫の途中に副作用が入る。つまり:

> **言えないことは、別の手段で無理やり言おうとする。**

だから語彙を揃えるのは利用者への親切ではなく、事故を防ぐ構造である。
「1 枠だけ差し替えたい」が言えなければ、AI は全部解放して取り直し、解放した
瞬間に戻った空き枠を自分で取り直す (§4 の実例)。悪意も怠慢も無く、**言える形が
無かった**だけで事故になる。

この目的は、AX の失敗を見つけたときの直し方も決める。直し方は「AI に気をつけ
させる」ではなく、**言えなかったことを言えるようにする** 側に倒す (P1 / §7 の
「直し方」欄)。

### 作る世界の手本は CLI、ただし 1 点だけ真似ない

AI がコードで安定して動くのは、CLI という整った世界があるからである。CLI は
**見て回れる / 辿れる / 組み合わせられる / すぐ確かめられる** の 4 性質を持ち、
AI はその使い方を大量に学んでいる。業務の世界はその逆で、道具は人の目のための
画面、状態は人の頭か古い表計算にあり、間違いが分かるのは何日も後である。
作業環境を作るとは、その世界に CLI の性質を一つずつ作ることである。

| CLI の世界 | 作業環境で作るもの |
|---|---|
| コマンドと `--help` | 型付きの操作と、受け取る鍵・鍵の形の宣言 |
| ファイルシステム | 文脈の木 (役ごとに歩ける範囲と描く中身) |
| git の履歴 | 追記専用の判定の列 |
| テスト | 受入条件と、実行とは別の評価役 |
| プルリクエストのレビュー | 外に出るものだけを止める承認の境界 |
| README | その業務のゲート図 |

**真似てはいけない違いが 1 つある。** CLI は `rm -rf` を許す。使うのが専門家で、
git で戻せるからである。送ったものが戻せない領域 (顧客への連絡、外部への送信、
資格行為) では、危険な操作は事前に封印し、承認の境界を CLI より固くする (P3)。

## 2. 計器の必然 — なぜ書いた本人は AX を測れないか

上の定義を認めると、次が **演繹的に** 導かれる:

- 実装中、書いた本人 (= author) は文脈が最大化する。命名の不一致や隠れた
  副作用に「慣れて」しまい、friction (= つまずき) が見えなくなる。
- つまり author は定義上 AX の値を測れない。慣れが friction を消すため。

したがって **独立した文脈ゼロのエージェントは、客観性のためではなく、
AX の唯一妥当な「計器」**。これはレビュー体制の好みではなく、AX の定義からの
必然。

**レビューの作法もここから決まる**: 計器 (= レビュアー) は author の説明を
読まずに、名前・スキーマ・エラー文言・戻り値だけで判断する。説明を読んだ
瞬間、それは文脈ゼロでなくなり計器として無効になる。

同じことが、同じ AI の中でも観測できる。**全部の文脈を持つメインのセッションでは
動き、文脈ゼロのサブエージェントでは間違える。** 差はモデルではなく、見えている
世界である。メインのセッションでは、会話の記憶が配線の穴を黙って埋めている。
だから **文脈ゼロのサブエージェントが間違えた場所は、配線の穴の場所** であり、
レビューはそこを探す作業になる。

## 3. 原則 (P1〜P8)

道具・データ・文脈の作り方を 8 つにまとめる。P1〜P6 は道具とデータの側、
P7・P8 は文脈と記録の側。各原則の **確かめる問い** を、そのままレビューの観点に
使う。

### 全原則に横断する 2 つのレンズ

次の 2 つは P1〜P8 のどれか 1 つに属するのではなく、**8 つすべてに当てる**。
独立した番号を持たないのは、どの原則の破れとしても現れるからである。

- **命名の一貫性** (レビュー出力では `naming`): 同じ概念は、コマンド・フラグ・
  フィールドを跨いで同じ名前を持つ。逆に、違う概念は違う名前を持つ。
  *Why*: AI は命名から意味を類推し、1 度覚えたパターンを他の操作へ転移する。
  命名不一致はその転移を毒し、静かな誤用を生む。
  *兆候*: 同概念で別名 / 別概念で同名 / 略記と正式名の混在 / 同義フラグが操作
  ごとに割れる。
  *実例*: `beacon doc` / `task` / `log` はマイルストーン指定が `-m`、
  `beacon milestone` は `--ms`。しかも無効な `-m` は黙って無視される (P6 と複合)。

- **最小驚き** (レビュー出力では `least-surprise`): 操作は名前が示唆するとおりに
  振る舞う。副作用は予測可能。
  *Why*: AI は名前から挙動モデルを組み立て、以後の予測に使う。驚きはその
  モデルを壊し、当該操作だけでなく **周辺の予測すべてを不確実化** する。
  *兆候*: 名前と挙動の乖離 / 隠れた副作用 (`status` 系が書き込む、read が
  cursor を進める) / 順序依存の暗黙前提 / モードで意味が反転する。

### 旧番号の読み替え (2026-11-05 の改訂前を引いている記述のため)

改訂前は 6 原則で、リポジトリ内のコメントやテストの docstring には今も
`AX 原則 N` の形で残っている。消さずに読めるよう対応を置く。**新しく書くものは
右側の名前を使う。**

| 旧 | 新 |
|---|---|
| 原則 1 命名の一貫性 | 横断レンズ **命名の一貫性** (番号を持たない) |
| 原則 2 silent no-op の禁止 | **P6** (黙って捨てない / 空を成功にしない) |
| 原則 3 エラーは回復経路を示す | **P6** (どうすれば通るかを書く) |
| 原則 4 フィールドは自己記述的 | **P5** (鍵とその形の宣言) |
| 原則 5 最小驚き | 横断レンズ **最小驚き** (番号を持たない) |
| 原則 6 破れは構造で塞ぐ | **P3** (経路ごと封じる) ＋ §6「直し方」欄 |

旧 6 原則に無く、今回ふえた軸は **P1 (操作の語彙) / P2 (読み戻し) / P4 (冪等) /
P7 (文脈が権限) / P8 (追記のみ)** の 5 つ。

### P1 操作の語彙を閉じる — CRUD を揃え、削除はキャンセルに置き換える

**性質**: AI がやりたいことを 1 つの操作で言える。操作に穴があると、AI は残りの
操作を組み合わせて穴を埋めようとし、その途中に副作用が入る。

**Why**: §1 の「作る側の目的」がそのまま理由になる。人間は「この操作が無い」と
言えるが、AI は黙って工夫する。**言えないことは、別の手段で無理やり言おうとする。**
削除は「かつてあったこと」を消すので、キャンセルにして記録を残す (P8 と対)。

**確かめる問い**:
- 道具が扱うもの (枠、承認カード、書類の依頼…) ごとに、作る・読む・変える・
  キャンセルするの 4 つが揃っているか
- 「変える」に、全体の置き換えだけでなく **「1 つだけ変える」粒度**があるか
- 削除の口が残っていないか。キャンセルには理由が必須か
- 業務で頻出する意図 (差し替え、除外、延期、取り消し、やり直し) が、**1 つの操作で
  言えるか**
- その語彙の中で、同じ概念が同じ名前を持っているか (横断レンズ: 命名の一貫性)

### P2 作れるものは読める。書いた結果がそのまま読める

**性質**: 作れるものには読む口がある。書いた直後に読むと、書いた結果が見える。

**Why**: 読めなければ、評価は「作れたか」を確かめられない。書いた直後の状態が
ずれて見えると、AI はそのずれを前提に次の手を打つ。

**確かめる問い**:
- 作れるものには、必ず 1 件を読む口と、一覧・検索の口があるか
- 書いた直後に読むと、書いた結果が見えるか (キャンセルしたものが「空き」では
  なく **「キャンセル済み」** として見えるか)
- 自分が置いたものと、他人が置いたものを、読んだ結果で区別できるか
- 読んだ結果が、名前から予想されるとおりか (横断レンズ: 最小驚き)

### P3 危険な操作は、禁止ではなく経路ごと封じる

**性質**: プロンプトの禁止文は守られないことがある。**持っていないものは使えない。**
外に届く操作は、人の承認を通らないと実行されない経路だけを置く。

**Why**: お願いベースの制約は AI が踏み外せる。経路が無いことは踏み外せない。
AX 欠陥は「気をつける」で消えない。

**確かめる問い**:
- 顧客や取引先に届く操作に、承認を経ずに実行できる経路が残っていないか
- 生データを渡すと作話できてしまう箇所で、**結果だけ**を返しているか (空き枠の
  一覧ではなく、押さえた枠だけを返す)
- 資格行為など、AI が触ってはいけない操作が、道具の宣言に **そもそも入っていないか**
- その封じ方は何段か (規約 / 既定拒否 / 記録に残る / 経路が無い)。迷ったら低い段に倒す

### P4 同じ操作を 2 回呼んでも壊れない

**性質**: 呼び直しや再配達は必ず起きる。途中まで成功した操作を呼び直すと、
副作用が二重になる。

**確かめる問い**:
- 操作ごとに「呼び直してよいか」が宣言されているか
- 副作用のある操作に、二重実行を防ぐ鍵 (指紋の id) があるか
- 途中で失敗したとき、**どこまで済んだか**が結果に返るか

### P5 見て回れ、辿れる

**性質**: 必要な情報を最初から全部渡すことはできない。参照を辿って取りに行ける
形にする。ただし辿れる範囲は役ごとに決める (P7)。

**Why**: AI はスキーマを一次情報として使う。名前が意味を担わないと、ソース読解が
毎回必須になり、読まなかったときに誤用する。

**確かめる問い**:
- 各操作に、受け取る鍵とその形 (日付の書式など) が宣言されているか。**形の無い鍵は、
  AI が当て推量する**
- 返り値に、次に辿るための参照 (id、確かめ先) が含まれているか
- 種類の違うものの id が、見た目で区別できるか。同じ形の id は、違うものを渡しても
  形として通ってしまう
- 名前だけで意味と型と単位が立つか (`timeout` が秒かミリ秒か不明、など)

### P6 失敗は、種類つきの文字で返す

**性質**: 失敗の種類を AI に分類させると、自分の失敗を自分で判定することになる。
**道具の側が分類して返す。**

**Why**: AI は「エラーが出ない = 成功」と解釈する。黙って捨てる (silent no-op) は
誤った成功確信を生み、間違いに気づく唯一の機会を奪う。**気づけない誤りは、
気づける誤りより桁違いに高コスト**。

**確かめる問い**:
- 「値を変えれば通りうる失敗」と「何を渡しても通らない失敗」を、道具が区別して返すか
- エラーの文に、何が足りなかったか・どうすれば通るかが書かれているか
- 受け付けられない入力を、黙って捨てていないか (無効フラグの無視、想定外引数の握り潰し)
- 空の結果を成功として返していないか (1 枠も取れなければ失敗として止める)
- 打ち間違えた操作名が、使い方を出して成功の終了コードで返っていないか
- **空が「無い」を意味するのか「見ていない」を意味するのかが、その面の言葉で分かるか。**
  中間的な面 (促し・一覧・キャッシュ) の空は、しばしば「条件を満たした」と
  読まれる。読み違えると事故になる空を返す面には、**その面自身に** 何を見ていないかを
  書く
- **取り違えの注記が、取り違える側の面にも在るか (開示は片側では閉じない)。**
  「X は Y ではない」と判断して注記を書いたなら、X 側だけでなく **Y 側** にも要る。
  片側だけの開示は「その注記を既に読んだ AI だけが回避できる防御」= 知識依存であり、
  AI はいつも新しい面から入るので届かない。直し方の勘所は、注記を増やすより
  **同じ事実を両面が同じ導出から出す**形に寄せること (重い場合でも、誤読される側に
  1 行置くのは安い)。
  *実例*: 「促し (トリガー) は関門ではない」が、新設した関門確認コマンドの help にだけ
  書かれ、実際に誤読される `beacon trigger check` 側は "Check pending triggers" のまま
  だった (2026-11-10)。空配列を見た AI が「関門が開いた」と読む経路は、記録に残る事故
  そのものの入口だった

**良い実例** (良い例も基準になる): `beacon task update` は引数不足時に完全な Usage を
返す。`beacon milestone observe` は「Pass --reason ...」と次の一手を明示する。

### P7 文脈は役ごとに絞る — 文脈が権限である

**性質**: 見えないものは判断できず、判断できないものは作話できない。守る相手は
**「実行したい側が、自分に都合よく判定すること」**である。

**確かめる問い**:
- 実行する役と、成立を判定する役が分かれているか
- 判定する役が読む証跡の文を、実行する AI ではなく、**道具の生の結果から機械が**
  作っているか
- 他の案件・他のターゲット (横) の情報が、その役の文脈に混ざっていないか
- 役に必要な情報が、届いているか (差し戻しの文面が実行役に届かない、など)
- 「何か無いか」という開いた問いを AI に投げていないか。やることが無ければ呼ばない

### P8 記録は追記だけ — 誰が、何を見て、何を判断したか

**性質**: 業務にはコンパイラが無い。**後から間違いを説明できること**が、その
代わりになる。

**確かめる問い**:
- 判定・実行・承認の記録に、更新・削除の口が無いか
- 「何も変わらなかった」も記録されているか (走っていないことと区別できるか)
- 判定の行から、そのとき AI に渡した文脈を辿り、再現できるか (時刻も含めて
  固定されているか)

## 4. 失敗の分類 (指摘を構造の修正に向ける)

テストやレビューで間違いが出たら、まず次の 4 つのどれかに分類し、対応する原則の
修正として直す。**指示で直すと会話の中に消えるが、構造で直せば残る。**

右端の「直す場所」は **修正の当たりどころの目安** であって、finding の `principle` 欄を
縛る対応表ではない。同じ分類でも破れている原則は別でありうる (例: 名前が黙って無視
される欠陥は、分類は「確かめられない」だが破れているのは P6 と命名の一貫性)。
独立レビューがこの列を制約と読み違えた実績があるので明記する。

| 分類 | 何が起きているか | 直す場所 (目安) |
|---|---|---|
| 届いていない | 必要な指示や事実が、その役の文脈に入っていない | P7 (役の許可リスト) |
| 指せない | 「最初の 1 枠」のような指し示しを、具体的な id や値に解決できない | P2・P5 (読める・辿れる・順序が決まっている) |
| 言えない | やりたいことを 1 つの操作で表せず、AI が組み合わせで工夫する | P1・P4 (操作の語彙) |
| 確かめられない | 間違った結果でも、受入条件を満たしてしまう | P2・P7 (受入条件と評価) |

### 実例 — 「最初の 1 枠はやめて、違う枠にして」

仮予定を 3 枠押さえたあとのこの差し戻しを、文脈ゼロのサブエージェントが間違えた。
正しくこなすには 4 つすべてが揃う必要がある。

1. **届いているか** — 差し戻しの文面が、実行役の文脈に入っているか
2. **指せるか** — 押さえた 3 枠の日時と id が順番つきで見えるか。「最初」が時刻順か、
   打診の文面の順かが決まっているか
3. **言えるか** — 道具には「発行」「確定」「全部解放」しか無かった。AI は全部解放して
   押さえ直したが、**解放した瞬間に最初の枠は空きに戻るので、同じ枠を取り直してしまう**
4. **確かめられるか** — 受入条件が「3 枠押さえた」だけだと、同じ枠を取り直しても成立になる

直し方は、「1 枠を差し替える」操作か「除外する日時」の引数を足し (P1)、受入条件に
「差し戻された枠を含まない」を足す (P7) ことである。**AI を責める余地はどこにも無い** —
言える形が無かっただけで、直す場所は環境の側にある。

## 5. 重さの付け方 (findings の重み)

重さは **影響** で付ける。影響が同じなら、**気づけるか** で上に倒す。
レビュー出力では前者が `severity`、後者が `detectability` に入る。

**キー名を `severity` から変えない。** 畳んだレポートを作る
``review_spine.aggregate_review_reports`` が全レビュー種別の finding から `severity` を
読んで重さの列を作るので、AX だけキー名を変えると **AX の指摘だけ重さが空になる**
(初版でこれを踏み、独立レビューが実測した)。値の語彙は種別ごとに違ってよいが、
**重さを載せるキーの名前は共有の契約**である。

| 重さ | 基準 |
|---|---|
| **顧客に届く** | 間違いが外に出る (誤送信、誤った確約、資格行為)。取り消せない |
| **手が失われる・二重になる** | 押さえた枠が消える、同じ操作が二重に走る、記録が壊れる |
| **人の手間が増える** | 誤りには直結しないが、やり直しや確認の手間を生む |

これに直交して、**気づけるか** を必ず添える。AI にとって最悪なのは失敗そのもの
ではなく、失敗が可視化されないことだからである。

- **silent**: 失敗が可視化されない (黙って捨てる / 空を成功として返す / 緑を返す
  ガード)。同じ影響なら最も重い
- **misleading**: エラーは出る (= silent ではない) が、真因と無関係な文言で誤診を
  誘発し、**誤った回復ループ**に入らせる。「見えているのに直せない」ため silent に
  次ぐ高コスト
  - 例: `Milestone not found` (真因は `--reason` の positional 誤流入) /
    `Entry not found: --help` (真因はヘルプ経路の破れ)
- **visible**: 失敗がその場で正しく見える

---

## 6. finding の形 (レビュー出力の単位)

指摘 1 件ごとに次の欄を埋める。**「どの原則の違反か」と「どの失敗につながるか」を
必ず書かせる**と、指摘が指示の工夫ではなく構造の修正に向かう。

| 欄 | 書くこと |
|---|---|
| 対象 | どの道具・操作・役の文脈・記録の話か |
| 原則 | P1〜P8 のどれに反するか (複数可。横断レンズに当たるならそれも) |
| 失敗の分類 | 届いていない / 指せない / 言えない / 確かめられない |
| 起きること | このままだと、AI がどう間違えるか。**具体的な依頼文と、その結果**で書く |
| 重さ | 顧客に届く / 手が失われる・二重になる / 人の手間が増える ＋ silent・misleading・visible |
| 直し方 | 操作・引数・返り値・受入条件・許可リストのどれをどう変えるか。**プロンプトの文言で直す案は、構造で直せない理由を添える** |

最後の欄が原則の要である。findings が提案する修正は「注意して使え」ではなく
**「物理的に誤りようがない」**形にする。プロンプト (= お願い) の制約は AI が踏み
外せるが、コード / スキーマ / 命名の制約は踏み外せない。

## 7. レビューの作法 (計器の使い方)

- **対象は diff**。問い: *この変更は上記の原則のどれかを新規に破る / 悪化させるか*。
  全 surface の総ざらい (= full-surface audit) は別モードで、PR ごとの軽量レビューとは
  分ける。
- **レビュアーは文脈ゼロの独立エージェント** (= cold subagent)。author の意図説明を
  読まず、名前・スキーマ・エラー・戻り値だけで判断する (§2)。

レビューする AI には、次の 3 つを守らせる。

1. **推測ではなく、道具の宣言・返り値・役の文脈を実際に読んだうえで指摘する。**
   読めなかったものは「未確認」と書く。新しく足された検査や台本は、静かに読むだけでは
   穴が出ない —— **走らせて破る**こと。
2. **業務で頻出する依頼 (差し替え、除外、延期、取り消し、やり直し) を一つずつ当てて、
   操作 1 つで言えるかを確かめる。** これが P1 を測る唯一の実地の方法である。
3. **指摘が無い原則も「問題なし」と明記し、何を当てたかを 1 行添える。** 見ていない
   ことと、問題が無いことを区別するためである。黙って飛ばすと、読み手は「見て問題が
   無かった」と読む。

   **裏付けの 1 行を要るようにしているのは、宣言だけなら無検証で埋められるから。**
   初版は `ok` / `unchecked` を裸の値で書かせていたが、独立レビューが「10 キー全部を
   無検証で `ok` と書いた出力と、実際に全レンズを当てた出力はスキーマ上区別できない」
   と指摘した —— 区別するために足した欄が、自己申告のままだったということ。いまは
   `ok` には **何を当てたか**、`unchecked` には **なぜ当てられなかったか** を書かせる。
   偽装のコストが上がり、読み手にも使える情報が残る。

多視点にするときは **failure-mode-diverse に**。各原則を別レンズとして独立に当てる。
同じ観点を N 体に増やす (= redundant) のではなく、語彙・読み戻し・封じ方・冪等・
辿れる・失敗の返し方・文脈・記録 を別々のレンズが見る。人間の多数決ではなく、失敗
モードの網羅が目的。

**証拠の prior (= 事前情報、optional)**: L2 記憶層に failure / surprise が蓄積して
いる capability への変更は、既に転んだ実績があるとみなして厳しく採点する。ただし
L2 が無い環境でも原則だけでレビューは成立する (= L2 は必須依存ではなく増強)。

## 8. この doc 自体の性格 (置き場所の判断軌跡)

- **Beacon CORE ではない**。CORE は Beacon 自身の設計原則。これは Beacon を
  (そして他の何でも) 作るときに使うメタツールの原典。
- dev インスタンス (= 開発職種パッケージ) が持つ横断 Capability (Layer 3、
  いずれ TrailNode で配布しうる領域) に随伴する。だから対象リポを選ばず、
  Beacon の DB (= beacon doc) ではなく **capability と一緒に旅する markdown
  ファイル** として置く。
- ここに書く原則は普遍的 (どの CLI / API / 業務の道具にも当たる)。Beacon 固有なのは
  §7 の L2 prior だけで、それも optional。

## 9. 良い AX の例 (full-surface レビューで surface から回収)

「良い実例も基準になる」に従い、計器が拾った良い surface を残す。新しい surface を
設計するときの手本 (= positive_observations の還元先):

- **context-free な安全弁**: `whoami` のような引数ゼロ・読み取り専用・自己記述的な
  identity/role 確認。破壊操作の前に文脈ゼロで叩ける。
- **enum を Usage 行にインライン列挙**: `--status ok|warning|error` /
  `--ball self|counterpart` / `--direction inbound|outbound`。閉じた値域が
  silent 誤分類を防ぐ。
- **ビジネスルールを必須フラグで構造化**: `operation approve --spec <doc-id>`
  (承認は必ず SPEC に紐づく、をプロンプトでなく必須フラグで強制)。
- **状態遷移ガードを Usage に開示**: `operation activate (todo/in_progress -> open)`
  — 状態機械が surface だけから読める。
- **日付書式を placeholder で固定**: `<YYYY-MM-DD>` は書式推測を構造的に消す。
  他の裸の `<date>` / `<datetime>` はこれに倣うべき手本。
- **必須は角括弧なしで明示**: `member remove --reason` のように必須フラグを
  非 optional 表記にすると、実行時エラーなしで必須が伝わる。
- **副作用を名前 / help で開示**: `pr sync --dry-run` / `member join` の
  "bind this cwd"。
- **引退した語彙を読む側だけ残す**: 産出が止まった種別を産出者台帳から外しつつ、
  読み手用の別辞書に説明ごと残す。過去の記録を引く人に「綴り違いでは」と誤って
  言わないための形 (P2 と P8 の交点)。
