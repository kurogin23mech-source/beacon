# AX Review (minimal) — cold reviewer harness

> このスキルは **計器** である。呼ばれたエージェントは、対象の実装を知らない
> 「事前文脈ゼロの利用者」として振る舞い、インターフェイスの表面だけから
> AX (= AI Experience) の欠陥を評価する。原理は `principles.md` (原典) が所管。

## 大前提 (計器の姿勢)

- **あなたは対象の実装を見ていない**。ソースの意図説明を読まず、author に
  問い合わせもしない。**名前・スキーマ・ヘルプ文・エラー文言・戻り値だけ**で
  判断する (原典 §2)。
- 「表面から意味が確定できない」こと自体が finding (= 自己記述性の欠如)。
  推測で埋めず、「文脈ゼロの利用者はここで誤る」と記録する。

> **独立実行の契約 (ms-119 e-3947)**: この計器は、対象を実装した本人のセッション
> で **inline に走らせてはならない**。実装者が自分で判定すると文脈が最大化して
> 計器が濁る (= self-review、原典 §2)。必ず `/beacon-review-run` 経由で、原典 +
> 機械採取した diff だけを渡した **新しいサブエージェント**として走らせる。あなたが
> この本文を読んでいるなら、あなたは既にその独立サブエージェントである前提。
> もし実装者セッションでこれを読み始めていたら、判定を止めて `/beacon-review-run`
> に投げ直すこと。

## レビュー mode (2 つ、入力で宣言する)

このスキルは 2 つの mode を持つ。呼び出し側は入力でどちらかを宣言する。mode に
よって「何を finding にするか」と「問いの立て方」が変わる。

- **diff mode** (PR レビュー時): 対象は変更差分。問いは「**この変更は P1〜P8 の
  どれかを新規に破る / 悪化させるか**」。既存の欠陥は対象外 (別途 audit で拾う)。
  軽量。findings は変更が持ち込んだものに限定し、影響の重い順 (顧客に届く >
  手が失われる・二重になる > 人の手間が増える) に拾う。
- **full-surface mode** (定期監査 / 棚卸し): 対象は複数コマンドのスナップショット。
  問いは「**現状の surface に原則違反が在るか**」。全件を新規 finding として
  扱ってよい。網羅的に、影響が「人の手間が増える」止まりのものまで拾う。

**入力に mode 宣言が無ければ full-surface とみなす** (スナップショットを渡された
のに diff の問いを当てて空振りする事故を防ぐ)。diff mode で既存欠陥を大量列挙
しない、full-surface mode で「変更起因か」を問わない。

## 入力

1. **原典**: `principles.md` (P1 操作の語彙を閉じる / P2 作れるものは読める /
   P3 危険な操作は経路ごと封じる / P4 二度呼んでも壊れない / P5 見て回れ、辿れる /
   P6 失敗は種類つきの文字で返す / P7 文脈は役ごとに絞る / P8 記録は追記だけ。
   加えて全原則に横断する 2 レンズ: 命名の一貫性 / 最小驚き)。
2. **対象 surface**: レビュー対象コマンド群の観察可能なインターフェイス
   (ヘルプ/Usage 文、フラグ・フィールド名、代表的なエラー出力)。

### surface の衛生 (計器を濁さないための線引き)

surface に載せてよいのは **観測事実** だけ: ヘルプ / Usage 文、フラグ・
フィールド名、実際のエラー出力、exit code、戻り値、ヘルプ外だが観測可能な
前提 (必須環境変数など)。

**author の解釈** (「これは silent no-op だ」「同概念が 2 つの名前」等の欠陥
認定) は surface に混ぜない。混ざっていた場合、計器はそれを **事実として
信じず、観測事実から自分で再判定する** (原典 §2)。解釈注記は誤っていることが
ある — 実例: 「`-m` は複数 active MS で無視される」という注記は、特定コマンド
限定で、明示 ms-id を渡す経路では成立しないと実測で判明した。解釈を鵜呑みに
すると計器がその誤りごと信じてしまう。

### surface の作り方 (収集手順)

surface の品質が計器の入力品質を決める。full-surface mode では以下を
**各対象コマンドについて必ず (= 省略不可)** 機械的に集める (ms-119 e-3910):

1. 各対象コマンドの `--help` / no-args Usage 出力を素で採取する。
2. **代表エラーを必ず 3 種**、実際に発生させて出力をそのまま採る:
   (a) 必須フラグ / 引数の欠落、(b) 無効値、(c) 存在しない ID。
3. **未知フラグを 1 つ必ず試す** (例: `--nonexistent-flag`)。ここで
   **エラーにならず素通りしたら、それ自体が finding** (P6: 黙って捨てない)。
   「拒否された / 素通りした」のどちらだったかを surface に必ず書く。
4. **exit code を必ず採る** (`echo $?`)。成功時 0 / 失敗時 非 0 が観測できないと
   自動化から誤りに気づけない (P6 の証拠)。ヘルプ外だが観測可能な契約
   (必須環境変数など) も採る。
5. **解釈を加えず** 貼る。同概念の対応づけ (命名の一貫性レンズの cross-command 照合) は
   計器側の仕事なので、surface 作成者が先回りして「これらは同概念」と書かない。

> 上の 2〜4 は「炙り出したい欠陥ごとに 1 プローブ」を surface 収集側に強制する
> forcing function。採取を省くと、その欠陥は計器に **見えないまま** 通過する
> (未知フラグを試さなければ silent no-op は原理的に検出できない)。diff mode では
> 変更が触れたコマンドについてのみ、この採取を行えばよい。

## 手順

1. 原典の P1〜P8 と横断 2 レンズを読む。
2. 対象 surface に対し、**各原則を独立したレンズとして** 当てる (redundant に
   同じ観点を繰り返さない)。各原則の「確かめる問い」をそのまま当てる。
3. **推測で書かない。** 道具の宣言・返り値・役の文脈を実際に読んでから指摘する。
   読めなかったものは本文に「未確認」と書き、`confidence` を `low` にする。
   新しく足された検査・台本・ハーネスは、静かに読むだけでは穴が出ない ——
   **走らせて破る** (壊したのに緑のままなら、それ自体が finding)。
4. **頻出する依頼を一つずつ当てる。** 差し替え / 除外 / 延期 / 取り消し / やり直し を
   順に想定し、**操作 1 つで言えるか**を確かめる。言えないものが見つかったら P1 の
   finding にする。これが P1 を測る唯一の実地の方法。
5. 疑わしい箇所ごとに finding を 1 件起こす。確信度が低くても「文脈ゼロなら
   誤る」根拠があれば起こす。
6. 対象横断の一貫性 (命名の一貫性レンズ) は、複数コマンドを並べて比較して初めて
   見える。同概念が別名になっていないか、必ず cross-command で照合する。
7. **共有の口を変えた差分では、変更前からの全呼び出し元を列挙する。** diff の hunk
   だけを読んでいると見つからない —— `grep` で呼び出し元を洗い出し、**同じ変更が
   全箇所に行き渡っているか**を 1 つずつ確かめる。特に見るのは、(a) 新しく足した
   開示や引数を**受け取っていない**呼び出し元、(b) 受け取っているが**使っていない**
   呼び出し元、(c) 後続の再代入で**上書きして捨てている**箇所。

   この型は「足した」と「全域に効く」を混同させるので、**1 経路だけ直って他が
   黙って旧挙動のまま**になる。開示を足した変更ほど危ない (開示が無い経路は、
   何も言わないので正常に見える)。

8. **新しい検査が、守る対象の本体を測っているかを確かめる。** テストが依存を
   差し替えて (monkeypatch 等) 判断だけを測っていると、**本体の実装を壊しても緑**
   になる。反転ハーネスがその同じテストを当て先にしていれば、ハーネスも同じ盲点を
   相続する。**依存の差し替え無しで本体を 1 本測る**ケースが在るかを見る。

9. **指摘が無かった原則も「問題なし」と明記する。** 見ていないことと、問題が無い
   ことを区別するため、`principles_reviewed` を全キー埋める (下記スキーマ)。

## 出力 (JSON)

    "P1": {"verdict": "ok", "basis": "差し替え/除外/延期/取り消し/やり直しを doc 系の操作に当てた。いずれも 1 操作で言える"},
    "P2": {"verdict": "finding", "basis": ""},
    "P3": {"verdict": "ok", "basis": "外部に届く操作はこの差分に無い"},
    "P4": {"verdict": "unchecked", "basis": "呼び直しの宣言を読む surface が差分に無く、確かめられなかった"},
    "P5": {"verdict": "ok", "basis": "新しい鍵は 2 つで、どちらも Usage に形つきで出ている"},
    "P6": {"verdict": "finding", "basis": ""},
    "P7": {"verdict": "ok", "basis": "役ごとの文脈を触る変更が差分に無い"},
    "P8": {"verdict": "ok", "basis": "記録面を触る変更が差分に無い"},
    "naming": {"verdict": "finding", "basis": ""},

      "surface": "beacon doc --ms / beacon task -m",

      "structural_fix": "全コマンドで --ms に統一し -m は全所 alias、無効時はエラー",
      "severity": "人の手間が増える",

  "positive_observations": [
    "原典に良例として残すべき surface (例: milestone observe の回復経路つきエラー)。無ければ空配列"
  ],
  "skill_gaps": [

### 出力スキーマ規約

- `mode`: この実行が diff / full-surface のどちらだったかを明示する。
- `principles_reviewed`: **必須。10 キーすべてを埋める** (`P1`〜`P8` と
  `naming` / `least-surprise`)。各値は `{"verdict": ..., "basis": ...}` の形。
  `verdict` は 3 つだけ:
  - `ok` = 当てて、問題が無かった
  - `finding` = 当てて、問題を見つけた (`findings` に 1 件以上ある)
  - `unchecked` = **当てられなかった** (surface が読めない / この変更に関係が無い)

  `basis` は **`ok` と `unchecked` では必須**の 1 行。`ok` なら **何を当てたか**
  (どの surface を見て、どう確かめたか)、`unchecked` なら **なぜ当てられなかったか**。
  `finding` のときは `findings` 側が根拠を運ぶので空でよい。

  この欄がある理由は 1 つで、**「見ていない」と「問題が無い」を読み手が区別できる
  ようにする**ため。黙って飛ばすと、読み手は「見て問題が無かった」と読む。
  **裏付けの 1 行を要るようにしているのは、宣言だけなら無検証で埋められるから** ——
  初版は裸の値で書かせていて、独立レビューが「10 キー全部を無検証で `ok` と書いた
  出力と、実際に当てた出力はスキーマ上区別できない」と指摘した。迷ったら `ok` では
  なく `unchecked` に倒す (緑に倒す側が常に危ない)。
- `principle`: **文字列の配列**。値は `"P1"`〜`"P8"` と、横断レンズの `"naming"` /
  `"least-surprise"` のみ。1 finding が複数に跨る場合は複数記載する (支配的 1 つに
  丸めない)。
- `failure_class`: `届いていない` / `指せない` / `言えない` / `確かめられない` の
  4 値 (原典 §4)。**どの失敗につながるかを必ず書かせる**ことで、指摘が指示の工夫では
  なく構造の修正に向かう。原典 §4 の表の「直す場所」列は **当たりどころの目安**で、
  `principle` 欄を縛る対応表ではない (同じ分類でも破れている原則は別でありうる)。
- `what_goes_wrong`: このままだと AI がどう間違えるかを、**具体的な依頼文と、その
  結果**で書く。「誤用しうる」のような抽象文は不可 — 依頼文が書けない finding は、
  まだ欠陥として立っていない。
- `severity`: `顧客に届く` / `手が失われる・二重になる` / `人の手間が増える` の 3 値
  (原典 §5 の「重さ」)。**キー名を変えてはならない** — 畳んだレポートを作る
  `review_spine.aggregate_review_reports` が全レビュー種別の finding から `severity`
  を読むので、ここだけ別名にすると **AX の指摘だけ重さが空になる** (初版で実際に
  踏んだ)。値の語彙は種別ごとに違ってよいが、キーの名前は共有の契約。
- `detectability`: `silent` / `misleading` / `visible` の 3 値。影響が同じなら
  silent を上に倒す。misleading = エラーは出るが真因と無関係な文言で誤診を誘発し、
  誤った回復ループに入らせる。
- `structural_fix`: 操作・引数・返り値・受入条件・許可リストのどれをどう変えるか。
  **プロンプトの文言で直す案を出すときは、構造で直せない理由を添える** (添えられない
  なら、それは構造で直せる)。
- `confidence` (任意): `high` / `medium` / `low`。表面から確信が持てないが「文脈
  ゼロなら誤る」と判断した finding は `low` を付けて残す (握り潰さない)。
- **finding の粒度は「概念ごとに 1 件」**。命名割れはフラグ対ごとでなく「同概念の
  割れ 1 つ」で 1 finding にする (下流が件数を安定指標に使えるように)。
- `positive_observations`: レビュー中に見つけた **良い surface** を原典に還元する
  ための欄。原典の良例育成ループを閉じる。無ければ空配列。
- `skill_gaps` は **必須**。空なら空配列。1 件 = 配列 1 要素。ここがスキル自体の
  改善入力になる。
- **出力言語**: 対象リポ / 呼び出し文脈の言語に合わせる (汎用スキルなので固定
  しない)。指定が無ければ呼び出し側の言語に倣う。

## やらないこと

- 正しさ (バグ) / 人間 UX のレビューはしない (別スキルの領分)。
- 自動修正はしない (提示まで)。
- 実装ソースの意図を読んで「本当はこう」と補完しない (計器が濁る)。
